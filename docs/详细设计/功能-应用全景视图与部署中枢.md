## 1. 背景与目标

### 1.1 诉求演进

| 阶段   | 诉求                                                                                                                                 | 落地                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 起点   | 导入三方应用改造部署后，记录部署情况；后期升级保持原先部署方法与标准，不因引擎变更漂移                                               | ✅ 已实现（`功能-部署需求清单与变更隔离.md`：`.anp/deploy.yaml` needs/actual + 引擎回填） |
| 发现 1 | `needs` 4 字段（mounts/env_keys/ports/command）引擎**只消费 config mount 一个**，其余 opencode 辛苦维护却无人看——文档骗人            | ❌ 待修                                                                                   |
| 发现 2 | 规则知识源（AGENTS.md）与引擎实现**已脱节 3 处**（端口段、CONFIG_PATH、needs 消费子集）                                              | ❌ 待修                                                                                   |
| 升级   | 在**应用视角**全维度（需求/研发/部署/运行/依赖）看到应用所有信息；后期开发/部署都依据它；改动自动更新；可视化友好；包括 ANP 平台自身 | 📌 本文档                                                                                 |

### 1.2 目标

建一个**应用维度的单一信息源**，三层统一：

1. **全景视图**（看）：按应用聚合全维度信息，只读、自更新、可视化
2. **部署需求中枢**（写）：`.anp/deploy.yaml` 的 needs 段作为部署的权威输入，opencode 智能备料 + 引擎确定性消费
3. **规则知识源**（地基）：`standard`/`AGENTS.md` 治理后，让 opencode 备料读到正确的 ANP 规则

让**开发有据可依、部署确定性可重放、opencode 智能备料有准确规则**。

## 2. 核心理念与架构总览

### 2.1 化解核心矛盾

用户诉求里有一个表面矛盾："后期开发依据这个信息做"（像权威中枢）+"有改变自动更新"（像派生聚合）。

**解法：分层各司其职**——

- 全景视图 = **只读聚合**（从各系统现 join，数据源变→下次拉取自动变，天然自更新，低风险）
- 部署需求文档 = **唯一权威写入**（人/opencode 维护 needs，驱动部署）
- 其余维度（需求/编码记录/部署历史/运行状态）= 各系统的派生数据，视图只读展示

### 2.2 三层架构

```
┌──────────────────────────────────────────────────────┐
│  应用全景视图（只读聚合看板 · 自更新 · 可视化）           │
│  需求 │ 研发(编码会话/异步任务/变更) │ 部署 │ 运行 │ 依赖 │
└──────────────────────────────────────────────────────┘
                         │
          部署维度内嵌一块「权威输入」（需主动维护）
                         ▼
┌──────────────────────────────────────────────────────┐
│  部署需求中枢 .anp/deploy.yaml（needs 段）              │
│  ├ opencode 部署前备料：读代码校验/生成 needs（P2）     │
│  └ 引擎确定性消费 needs：port/command/env/mount（P1-b） │
└──────────────────────────────────────────────────────┘
                         │
                         ▼ 地基
┌──────────────────────────────────────────────────────┐
│  规则知识源治理（standard/AGENTS.md 补全 + 常量防漂移）   │
│  ← 让 opencode 备料读到正确的 ANP 规则（P1-a）          │
└──────────────────────────────────────────────────────┘
```

## 3. 现状分析（事实基线）

### 3.1 全景视图数据分布（约 70% 就绪）

聚合基础已存在：`Store.Detail()`（`internal/appdeploy/detail.go:53`）已 join 需求/变更/发布/部署实例/git 提交 5 张表。

| 维度                | 数据源（表/来源）           | app 关联键                                   | 现状                | 汇聚工作量                                       |
| ------------------- | --------------------------- | -------------------------------------------- | ------------------- | ------------------------------------------------ |
| 需求                | `requirement`               | `application_id`                             | ✅ 齐全             | 极小（Detail 已 join）                           |
| 变更                | `change_request`            | `application_id`+`source_id`                 | ✅ 齐全             | 极小（Detail 已 join）                           |
| 发布                | `release_record`            | 经 change 派生                               | ✅ 齐全             | 极小（Detail 已 join）                           |
| 部署实例(test/prod) | `appdeploy_instance`        | `app_id`                                     | ✅ 齐全             | 极小（Detail 已 join）                           |
| git 提交            | repo git log                | repo_dir                                     | ✅ 齐全             | 极小（Detail 已 join）                           |
| 中间件依赖          | `appdeploy_service_binding` | `app_id`                                     | ✅ 齐全             | 小（并入 Detail，复用 `ListDeps`）               |
| 编码会话            | `codews_session`            | `app_id`（列已存在）                         | 🟡 有数据无查询方法 | 小（加 `ListSessionsByApp`，套 performance SQL） |
| 异步编码任务        | `code_task`                 | 无 `app_id`，靠 `source_id`/`change_id` 派生 | 🟡 要派生           | 中（派生 JOIN 或加列回填）                       |
| 路由表              | `appdeploy_route`           | `app_id`                                     | 🟡 有列无读方法     | 小（加 `ListRoutesByApp`）                       |
| **部署历史时间线**  | 无表                        | —                                            | ❌ 缺               | 大（新建 `deploy_history` + 采集）               |
| **应用级监控趋势**  | 实时 docker stats，不入库   | —                                            | ❌ 缺               | 大（新建 app 指标采集）                          |
| **健康检查历史**    | 仅当前态                    | —                                            | ❌ 缺               | 中-大（新建健康事件采集）                        |

**结论**：主体是纯聚合展示。第一版（P1-c）覆盖前 9 行，几乎不动数据采集；后 3 行（部署历史/监控趋势/健康 SLA）是 P3 独立采集。

### 3.2 规则知识源脱节（3 处，P1-a 修）

opencode 经仓库根 `AGENTS.md` 了解 ANP 规则（`standard/model.go:97-108` 固定段 → `BuildAgentsMarkdown` → `RefreshAgentsMD` 写入 → opencode `--dir` 加载）。文字层能跟升级，但**引擎实现细节散落在 `appdeploy/*.go`，没同步进 AGENTS.md，已脱节**：

| 脱节点             | 引擎实际（代码）                                                  | AGENTS.md 是否告知 opencode          |
| ------------------ | ----------------------------------------------------------------- | ------------------------------------ |
| 端口段             | `deployer.go:17-22`：test 9100-9199 / prod 9200-9300              | ❌ 完全没写                          |
| CONFIG_PATH 注入   | `handler.go:1931`：自动注入 `CONFIG_PATH=/app/config.yaml`        | ❌ 没写                              |
| PORT 注入          | `deployer.go:91-98` `ensurePortEnv`                               | ❌ 没写                              |
| needs 实际消费子集 | `deploy_manifest.go:144`：只读 `mounts` 里 `dst=/app/config.yaml` | ❌ 让 opencode 维护全 4 字段（骗人） |

且**部署链路（`Deploy`/`buildAndDeploy`）0 次 `RefreshAgentsMD`**。

### 3.3 needs 消费缺口（P1-b 修）

`buildAndDeploy`（`handler.go:1806`）对 `mf`（manifest）只引用 3 处：加载、`ResolveConfigMount`（仅 config）、`RecordActuals`。`needs.ports/command/env_keys` 在生产代码**零消费**。缺 manifest 时软回退（不阻断）。零部署前校验。

## 4. 方案设计

### 4.1 P1 地基 + 聚合（第一版）

#### P1-a 规则知识源治理（地基，最先做）

**目的**：让 opencode（备料/适配/编码）读到**与引擎实现一致**的 ANP 规则。

1. **补全 AGENTS.md 固定段**（`standard/model.go:97-108`）四条事实：
   - 端口段 test 9100-9199 / prod 9200-9300
   - ANP 自动注入 `CONFIG_PATH=/app/config.yaml` 和 `PORT`，应用应读这两个 env
   - needs 实际消费子集：**当前引擎只消费 `mounts`（且 dst=/app/config.yaml）；`ports/command/env_keys` 为预留，待 P1-b 接入后生效**
2. **常量共享防漂移**（治本）：端口段等常量从 `deployer.go` 的 const 引用到 `model.go` 渲染，改一处自动进 AGENTS.md——不再靠人脑对齐
3. **部署链路补 `RefreshAgentsMD`**：`Deploy` handler 入口加一次刷新（为 P2 备料铺垫）

**不做**：暂不把固定段挪成 DB 记录（保持 Go 字面量 + 常量共享，门槛可接受；热更新需求出现再迁移）。

#### P1-b 引擎消费 needs 全字段

**目的**：让 opencode 维护的 needs 真正生效（否则备料白做）。

在 `buildAndDeploy` 接上：

| needs 字段 | 消费方式                                                                      | 优先级   |
| ---------- | ----------------------------------------------------------------------------- | -------- |
| `ports`    | 容器监听端口优先取 `needs.ports[0]`，回退 `a.InternalPort`                    | 高于 DB  |
| `command`  | `docker run` 追加启动命令覆盖镜像 CMD                                         | 覆盖镜像 |
| `env_keys` | 校验声明的 env 是否有值来源（DB/mwReconciler），缺失记 WARN（软提示，不阻断） | 校验为主 |
| `mounts`   | 全部挂载（不只 config.yaml）                                                  | 扩展现有 |

保留"缺 manifest 软回退"设计（best-effort 不阻断），但加日志可见性。

#### P1-c 全景视图聚合（看板）

**后端**：扩 `Store.Detail()`（`detail.go`）→ 新 `AppFullView` 结构，在现有 5 表基础上 join：

- 编码会话：加 `ListSessionsByApp(appID)`（复用 `performance/store.go:84-92` SQL，换 app_id）
- 异步任务：派生 `code_task`（经 source_id/change_id）
- 依赖：并入 `ListDeps`
- 路由：加 `ListRoutesByApp`

**前端**：把现有内联三列面板（`applications/page.tsx:1883-1978`）升级为全景布局：

```
┌─ 应用头：name/kind/mode/version + 各环境状态徽标 ──────────┐
├─ 需求 ───┬─ 研发 ───┬─ 部署 ───┬─ 运行 ───┬─ 依赖 ────┤
│ 需求列表  │ 编码会话  │ 实例test/ │ 资源当前  │ 中间件绑定│
│ 状态/优先 │ 异步任务  │ prod+URL  │ 健康徽标  │ deps声明  │
│          │ 变更记录  │【部署需求 │          │          │
│          │ git提交   │  文档★】  │          │          │
└──────────┴──────────┴──────────┴──────────┴──────────┘
  ★ = 部署维度内嵌 .anp/deploy.yaml needs（权威输入，可编辑）
```

**自更新**：`Detail()` 实时聚合，前端延续现有轮询（stats 30s）；数据源变→下次拉取自动变。

**包括 ANP**：ANP 平台自身登记为一条 `application` 记录（自描述），复用同一视图与同一套聚合。

### 4.2 P2 opencode 部署前备料（智能备料）

**触发**：每次部署都跑（用户定：最稳妥）。

**流程**（`Deploy` handler 内、`buildAndDeploy` 前）：

```
点「构建部署」
 → RefreshAgentsMD（拿最新规则）
 → 起 opencode（复用 dev/coding.go 的 opencode run），prompt=梳理仓库+校验/生成 needs
   · 无 .anp/deploy.yaml → 按代码生成完整 needs
   · 有 → 校验端口/命令/config/Dockerfile，缺或过时则补全
 → needs 无需改动 → 直接进 buildAndDeploy（不弹确认）
 → needs 要改动 → 前端弹 needs diff，确认后写入仓库再部署
 → opencode 备料失败 → 降级用现有 needs 继续 + 告警（不卡死）
 → buildAndDeploy 按 needs 确定性部署（P1-b 已接消费）
```

**校验粒度**（用户定基调）：关键字段硬校验（端口/启动命令/config/Dockerfile），`env_keys` 软提示（缺值告警不阻断）。

**与导入适配的区别**：`SubmitAdapt` 是一次性大改代码适配 ANP；本环节是每次部署前的轻量 needs 校验，不动业务代码。

### 4.3 P3 可观测采集（独立立项）

补 3 块真缺口，新建采集表 + 任务：

- **部署历史时间线**：`deploy_history`（who/when/env/sha/version/result），每次 deploy 写一条
- **应用级监控趋势**：app 级 cpu/mem 周期采样持久化（现有 monitor 是节点级）
- **健康检查历史/SLA**：健康事件采集（现有只当前态）

P3 与 P1/P2 解耦，可独立排期。

## 6. 关键决策记录

| 决策                 | 选择                             | 理由                                                               |
| -------------------- | -------------------------------- | ------------------------------------------------------------------ |
| 全景视图性质         | **只读聚合**（非权威中枢）       | 数据都在各系统，聚合最自然、自更新、低风险；只有部署需求是权威写入 |
| opencode 备料触发    | **每次部署都跑**                 | 最稳妥，needs 永不与代码脱节（用户定）                             |
| needs 改动确认       | **只动文件时弹 diff 确认**       | 平时一键过，文件要变才拦                                           |
| 校验粒度             | 关键字段硬校验 + env_keys 软提示 | 避免 opencode 误判卡死部署                                         |
| 缺 manifest          | **软回退不阻断**（保留现状）     | best-effort 设计意图，加日志可见性                                 |
| needs 字段消费优先级 | needs 优先于 DB/镜像             | needs 为权威，DB/镜像回退                                          |
| ANP 自身             | 登记为 application 复用同视图    | 统一，不自建                                                       |
| 固定段载体           | 暂留 Go 字面量 + 常量共享        | 门槛可接受，热更新需求出现再迁移 DB                                |

## 7. 不做 / follow-up

- ❌ 全景视图做成"权威中枢"（写它驱动各系统）——风险高收益不明，只读聚合已满足
- ❌ P1 阶段补部署历史/监控趋势/健康 SLA 采集——P3 独立立项
- ❌ 固定段挪 DB 热更新——暂不需要
- 📌 follow-up：`.anp/deploy.yaml` 旧 needs 残留字段（env_keys/ports/command）的历史应用，P1-b 接入后自然生效；P2 备料会逐步校准

## 8. 验证策略

**P1-a 规则源**：改 `model.go`+常量后，`RefreshAgentsMD` 产出的 AGENTS.md 含端口段/CONFIG_PATH/needs 真相；常量改一处两边同步（单测断言）。

**P1-b needs 消费**：`buildAndDeploy` 单测——给 needs.ports/command，断言 docker run 参数用了 needs 值；缺 needs 回退 DB。

**P2 备料**：.28 e2e——无 deploy.yaml 的应用点构建部署，opencode 生成 needs（确认弹 diff）；有 deploy.yaml 但代码改了端口的，opencode 提示补全。

**整体**：每个 P 独立 commit + 部署 .28 + 用户浏览器 e2e；P1 全程不改表，可独立合 main。
