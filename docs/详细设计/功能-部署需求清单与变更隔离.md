# 功能：部署需求清单（.anp/deploy.yaml）与变更隔离

> 状态：设计（待评审） ｜ 日期：2026-08-09 ｜ 关联事故：yxt-eino-v2 测试部署崩溃（config.yaml 挂载源路径漏转宿主路径）

## 1. 背景与问题

### 1.1 事故

yxt-eino-v2（企业微信机器人）测试部署后启动即崩：容器 `Exited(1)`，日志 `read /app/config.yaml: is a directory`。

**根因**：`buildAndDeploy` 中 config.yaml 的 docker 挂载源路径用容器内路径 `/data/repos/<app>/config.yaml`，而 backend 经**宿主 docker socket** 跑 `docker run -v`，daemon 在宿主机解析源路径——该容器内路径在宿主不存在，Docker 自动建空目录，挂成「目录挂到文件」，应用读配置即崩。**漏调 `toHostRepoDir`** 是直接原因（PR #17 已修）。

### 1.2 系统性缺陷（用户诉求）

事故暴露的不是单点 bug，而是 ANP 部署引擎的三个缺陷：

1. **部署方式全靠代码临时推导，无记录**——挂载哪些文件、注入哪些 env、开哪些端口，全由运行中的 backend 代码现场计算，从不落盘。推导逻辑一处漏了（如本次 toHostRepoDir），事后无从查证「上次成功部署到底挂了什么」。
2. **无部署可复现性**——重新部署是「用最新代码重新推导」，不是「照上次成功的部署规格走」。平台升级会悄悄改变一个已经能跑的应用的部署行为。
3. **无变更隔离**——deploy 引擎的改动与「已部署应用的运行契约」之间没有边界。升级引擎即风险所有已部署应用。

用户原话："ANP 负责导入三方应用、改造后部署，应当记录所有的部署情况；以后再开发升级，应当保持原先的部署方法跟标准，不能每次开发影响后期运行。"

## 2. 目标与非目标

### 2.1 目标（本期，周一前）

- **记录所有部署情况**：每次部署的完整规格（挂载/env/端口/命令/镜像 digest/引擎版本）落盘为应用仓库内的可见文件。
- **部署读规格、不再盲推导**：重新部署时读取已记录规格，按规格走；让「部署方法与标准」成为随代码版本走的、可见、可审、可改的开发产物。
- **复用导入适配机器**：不另造机制，沿用导入三方应用时已有的 `AGENTS.md`（标准）+ `AdaptPrompt`/`SubmitAdapt`（opencode 维护）+ `.anp/deps.yaml`（规格文件）范式。

### 2.2 非目标（后续演进，不在本期）

- opencode 真正执行部署（读规格 + 现状，自适应新部署/升级优化）。本期部署仍由现有引擎执行，仅使其读规格。
- 部署历史版本化（多版本快照、回滚到任意历史规格）。本期为「每应用+环境单一当前规格文件」。
- 引擎版本门禁 / 规格变更对比告警。

### 2.3 周一范围小结

就 4 处小改：扩标准段 + 定义 `.anp/deploy.yaml` + 部署时读 + 部署后回填。全部顺着现有机器加，缺失规格文件时退回现状行为，**零回归**。

## 3. 核心思路：复用导入适配机器

导入三方应用时，ANP 已有一套「让 opencode 把应用适配成可部署」的完整机器（`handler.go` 导入路径 1443-1458）：

```
① SeedFromManifest   读 repo 的 .anp/deps.yaml → DB（声明中间件依赖）
② RefreshAgentsMD    把「ANP 部署适配规范」标准写进 repo 的 AGENTS.md
③ SubmitAdapt        把 AdaptPrompt 喂给 opencode → opencode 照 AGENTS.md 改应用 + 写 .anp/deploy.yaml + 提交
```

其中 `AGENTS.md` 的「ANP 部署适配规范」段是固定文本，由 `standard.BuildAgentsMarkdown`（model.go:97-107）生成——**这就是用户所说「部署方法跟标准」的载体**。

**本设计的核心**：把「部署需求记录」作为 `.anp/deps.yaml` 的亲兄弟——同样由 opencode 在 repo 里维护、ANP 消费、AGENTS.md 标准驱动。四处改动全部是给这套现成机器加一个「deploy 规格」维度：

| 现有（deps 维度）                      | 本期新增（deploy 规格）                      |
| -------------------------------------- | -------------------------------------------- |
| `.anp/deps.yaml`（中间件依赖声明）     | `.anp/deploy.yaml`（部署运行规格）           |
| `SeedFromManifest` 读 deps→DB          | `LoadDeployManifest` 读 deploy 规格→驱动部署 |
| AGENTS.md「依赖声明」bullet            | AGENTS.md「部署需求回写」bullet              |
| opencode 经 SubmitAdapt 维护 deps.yaml | opencode 经同一 SubmitAdapt 维护 deploy.yaml |

## 4. 设计详述

### 4.1 扩展 AGENTS.md「ANP 部署适配规范」标准段

`standard/model.go` `BuildAgentsMarkdown` 末尾固定段（第 103 行 deps.yaml bullet 之后）增加一条：

```
- **部署需求回写（.anp/deploy.yaml）**：导入/适配/开发后，在仓库根维护 .anp/deploy.yaml
  记录本应用的部署运行规格（挂载的文件、需要的 env key、内部端口、启动命令）。ANP 部署时
  读取此文件按规格部署（不盲推导），部署成功后回填实际值（镜像 digest、解析出的宿主路径、
  host 端口、引擎版本）。格式见下方。无部署特殊需求可不写，ANP 将按默认推导并回填生成。
```

> `AdaptPrompt` 已要求 opencode「严格按 AGENTS.md 的『ANP 部署适配规范』改」，故标准段一扩，opencode 导入适配时即会维护 `.anp/deploy.yaml`，无需改 prompt。

### 4.2 `.anp/deploy.yaml` 文件格式

位置：`<RepoDir>/.anp/deploy.yaml`（与 `.anp/deps.yaml` 同目录，应用仓库根的 `.anp/` 下）。

```yaml
# 部署运行规格 —— opencode/开发维护「需求」部分；ANP 部署成功后回填「实际」部分
# 字段标注 [需求]=开发/opencode 维护，[实际]=ANP 回填
mounts: # [需求] 需挂载的文件
  - src: config.yaml # 相对 RepoDir 的路径（可移植）
    dst: /app/config.yaml # 容器内目标路径
    mode: ro
env: # [需求] 需要的 env key（只记 key 名，值不下盘）
  - CONFIG_PATH
  - REDIS_ADDR
ports:
  internal: 80 # [需求] 应用监听端口
command: ["/app/server"] # [需求] 容器启动命令

# —— 以下 ANP 部署成功后回填（实际）——
image: appdeploy-yxt-eino-v2:test-v7 # [实际]
image_digest: sha256:abc123... # [实际] 镜像精确指纹
resolved: # [实际] 实际解析值（审计/确定性重放用）
  mounts_src: # 与 mounts 一一对应的宿主绝对路径
    - /opt/anp/data/repos/yxt-eino-v2/config.yaml
  host_port: 9107
engine_version: 3b3663b # [实际] 部署所用 backend 代码版本(git sha)
updated_at: "2026-08-09T13:58:04Z" # [实际]
updated_by: anp-deploy # [实际] anp-deploy | opencode | dev
```

**密钥安全**：`env` 只记 key 名，不存值。部署时值从 `appdeploy_env` + mwReconciler 实时解析（密钥不下盘、中间件绑定变更能生效）。

### 4.3 部署时读取规格（`LoadDeployManifest`，`SeedFromManifest` 的兄弟）

新文件 `internal/appdeploy/deploy_manifest.go`：

- `type DeployManifest struct { Mounts []MountSpec; Env []string; Ports PortSpec; Command []string; Image, ImageDigest string; Resolved ResolvedSpec; EngineVersion, UpdatedAt, UpdatedBy string }`
- `func LoadDeployManifest(repoDir string) (*DeployManifest, error)`：读 `<repoDir>/.anp/deploy.yaml`；文件不存在返 `(nil, nil)`；解析失败返 err（调用方 best-effort 降级）。

接入点 `buildAndDeploy`（handler.go ~1886-1897），在计算 configPath/envPairs 之前：

```
m, mErr := LoadDeployManifest(a.RepoDir)
if mErr != nil { zap.Warn(...) }   // 规格损坏：记录 + 退回推导，不阻塞
if m != nil {
    // 按规格驱动挂载/env/端口/命令（而非盲推导）
    configPath = resolveMountsFromManifest(m, a.RepoDir)   // 见下「读语义」
    envPairs = resolveEnvKeys(m.Env, a.ID, ctx)            // 值实时解析
    internalPort = m.Ports.Internal
    // command 同理（若规格给出）
} else {
    // 现状：configPath = toHostRepoDir(detectConfigPath(a.RepoDir)); envPairs, _ = ...
}
```

**读语义（确定性 vs 可移植性的平衡）**——对每个 mount：

- 若 `resolved.mounts_src[i]` 已记录**且该宿主路径文件存在** → 直接用（**确定性优先**：哪怕 toHostRepoDir 代码再坏，照记录的宿主路径走，应用不崩）。
- 否则 → 用相对 `src` 经 `toHostRepoDir(filepath.Join(repoDir, src))` 解析（可移植：换部署机也能算对）。

> 这条「resolved 优先」是直接防住本次事故同款 bug 的关键：一次成功部署把正确宿主路径记进 `resolved`，之后即便 toHostRepoDir 推导逻辑被改坏，重部署仍读记录的正确路径。

### 4.4 部署成功后回填实际

`buildAndDeploy` 中部署成功（`ins.Status = "running"`）后，构建 manifest 实际值并写回：

- `image` = 实际镜像 tag；`image_digest` = `docker inspect` 取 `RepoDigests`/`Digest`（deployer 已有 docker 访问）。
- `resolved.mounts_src` = 本次实际挂载的宿主路径列表（与 mounts 一一对应）；`resolved.host_port` = `ins.HostPort`。
- `engine_version` = 包级变量 `EngineVersion`（构建期 ldflags 注入 git sha，见 §4.6）。
- `updated_at` = 部署时间；`updated_by = "anp-deploy"`。
- 保留「需求」部分（mounts/env/ports/command）不动——只覆盖「实际」部分，开发维护的需求不被回填覆盖。

`func WriteDeployManifest(repoDir string, m *DeployManifest) error`：合并读入的现有规格（保需求）+ 实际值，原子写 `<repoDir>/.anp/deploy.yaml`。

**仅成功才写**：部署失败不覆盖好规格（文件永远=上次成功标准）；失败原因仍在现有 `instance.last_error/build_log`。

### 4.5 opencode 维护规格（复用 SubmitAdapt，零新增触发逻辑）

- 导入时 `SubmitAdapt(ctx, psID, appID, repoDir, AdaptPrompt(name))` 已触发——AGENTS.md 标准段扩了「部署需求回写」后，opencode 适配时即生成 `.anp/deploy.yaml` 的「需求」部分。
- 开发完升级：再触发 `SubmitAdapt`（或开发在 worktree 内自行维护），opencode 据 AGENTS.md + 现状调整 `.anp/deploy.yaml`，提交回主仓。
- 部署时 ANP 读 `.anp/deploy.yaml`（主仓 RepoDir 路径），需求随提交流转。

### 4.6 引擎版本注入

`internal/appdeploy`（或 main）加 `var EngineVersion = "dev"`，构建期 `-ldflags "-X zhiyuan-anp/platform/backend/internal/appdeploy.EngineVersion=$(git rev-parse --short HEAD)"` 注入。回填写入 manifest 供审计「哪份代码部署的」。部署脚本（`deploy/`）的 build 步骤补此 flag。

## 5. 数据流

**导入新应用**：

```
SeedFromManifest(deps) → RefreshAgentsMD(写含部署规格段的 AGENTS.md) → SubmitAdapt
  → opencode 适配应用 + 写 .anp/deploy.yaml(需求) + 提交
首次部署 → 引擎读 .anp/deploy.yaml(或推导) → 部署成功 → 回填实际
```

**开发后升级**：

```
开发(改代码+按需改 .anp/deploy.yaml 需求) → 测试 → 部署
  → 引擎读 .anp/deploy.yaml(resolved 优先) → 重新构建镜像 → 按规格部署 → 回填新实际
```

**事故复盘**：

```
yxt-eino-v2 部署崩 → 查 .anp/deploy.yaml 的 resolved.mounts_src / engine_version
  → 立刻看到挂了哪个宿主路径、哪份代码部署的，无需翻代码推导
```

## 6. 错误处理与降级（全部 best-effort，绝不阻塞部署）

| 情况                                 | 处理                                          |
| ------------------------------------ | --------------------------------------------- |
| `.anp/deploy.yaml` 不存在            | 退回现状推导（detectConfigPath 等），零回归   |
| 文件存在但 YAML 解析失败             | WARN 日志 + 退回推导，不阻塞                  |
| `resolved` 记录的宿主路径不存在      | 退回相对 src + toHostRepoDir 解析             |
| 写回失败（磁盘满/权限）              | WARN 日志，部署仍成功（记录缺失但不影响运行） |
| `image_digest` 取不到                | 留空，其余照写                                |
| `EngineVersion` 未注入(ldflags 没配) | 记 `"dev"`                                    |

## 9. 与现有机制的关系

- **`.anp/deps.yaml`**：亲兄弟。deps 声明中间件依赖（→ mwReconciler 注入连接 env）；deploy.yaml 声明部署运行规格（→ 引擎驱动挂载/env/端口）。两者同由 opencode 维护、AGENTS.md 驱动。
- **`deployNative` 的 `deploy.yaml`**：**不同方向**。那是应用自带的 native 部署配方（用户预先写好，ssh/winrm 节点）。本设计的 `.anp/deploy.yaml` 是 ANP 记录/维护的容器部署规格（docker 引擎消费）。名字用 `.anp/deploy.yaml`（带 `.anp/` 前缀 + 在 `.anp/` 目录）与根目录的 `deploy.yaml` 错开，不混淆。
- **`appdeploy_instance`**：维持现状作「当前态」摘要（status/build_log 等）。`.anp/deploy.yaml` 是部署规格的持久、可见、随代码版本走的载体，与 instance 互补。

## 10. 后续演进（本期不做）

1. **opencode 执行部署**：`.anp/deploy.yaml` 已为 opencode 可读的结构化规格预留；后续让 opencode 读规格 + 现状，自适应新部署或基于已有部署升级优化，引擎退为下层工具。
2. **部署历史/回滚**：在 `.anp/` 下保留多版本规格快照（如 `.anp/deploy.<version>.yaml`），支持回滚到任意历史规格。
3. **引擎版本门禁**：部署时比对 `engine_version` 与当前引擎版本，跨版本变更给告警/审批。
4. **规格变更对比**：开发提交改了 `.anp/deploy.yaml` 的需求部分时，diff 提示对运行的影响。
