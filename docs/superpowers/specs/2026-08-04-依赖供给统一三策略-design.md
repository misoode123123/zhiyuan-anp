# 依赖供给统一三策略（KindSpec）设计

> 日期：2026-08-04 ｜ 状态：设计（待评审） ｜ 相关代码：`internal/mwsupply`、`internal/pgsupply`、`internal/appdeploy`

## 1. 背景

当前 ANP 的有状态中间件供给分两套、不统一：

- **mwsupply**（redis/milvus）：**声明驱动**（`.anp/deps.yaml` / 「🔗 中间件依赖」UI），支持 `bind_existing` / `shared` / `dedicated` 三策略；供给主逻辑按 kind 做 switch 分派。
- **pgsupply**（PG）：独立包，**自动供给**（每个 managed app 默认建一个库 in 项目空间共享 PG，≈ shared），**仅 shared、无 bind_existing / dedicated、不声明**。

割裂带来的问题（实例：eino 客服系统导入）：

- PG 自动给、redis/milvus 要声明 → 创建者心智不一致。
- PG 缺 bind_existing / dedicated → 无法指已有 PG、无法起独立 PG。
- 新增 kind（kafka/mysql/es…）要改 mwsupply 多处 switch（`supplyShared` / `supplyDedicated` / `launchDedicated` / `writeSharedEnv` / `writeDedicatedEnv`），成本高、易漏。
- 依赖连接信息常被手填 env（绕过供给）→ 游离、无隔离、不可纳管、不可回收。

## 2. 目标

把有状态中间件供给**统一**为一套声明驱动的三策略模型，且**可扩展**：

- 所有有状态 kind（redis / milvus / pg + 未来 kafka / mysql / es…）走同一套 `bind_existing` / `shared` / `dedicated`。
- 创建者在**创建 / 导入 / 开发**时声明 kind + strategy。
- 加新 kind = 注册一个 KindSpec，供给主逻辑零改动。

## 3. 关键决策

| 决策     | 选定                                 | 理由                                                      |
| -------- | ------------------------------------ | --------------------------------------------------------- |
| 覆盖范围 | 仅**有状态中间件**                   | 三策略本质是隔离有状态数据；无状态服务（网关/代理）不纳入 |
| PG 语义  | **声明驱动**（与 redis/milvus 一致） | 模型一致；存量自动 PG 平迁为 declared `pg=shared`         |
| 实现路线 | **A：KindSpec 注册表**               | 扩展性最好；pgsupply 收编为 pg 的 spec，消除两套割裂      |

## 4. 架构

### 4.1 KindSpec —— 每个 kind 的供给规格

把现在散在 mwsupply 各 switch 里的 per-kind 差异，收敛成一个声明式规格：

```go
// TokenKind 描述 shared 策略下"实例内隔离 token"的语义。
type TokenKind int
const (
    TokenDBNumber        TokenKind = iota // redis：db 号池
    TokenCollectionPrefix                 // milvus：collection 前缀
    TokenDatabaseName                     // pg：每 app 一个库（库名即 token）
    // 未来：TokenTopicPrefix(kafka) / TokenIndexPrefix(es) ...
)

type EnvKV struct{ Key, Value string; IsSecret bool }

type KindSpec struct {
    Kind      string   // "redis" | "milvus" | "pg" | ...
    AddrEnv   string   // 主连接键：REDIS_ADDR / MILVUS_ADDR / DATABASE_URL(pg 特例)
    TokenKind TokenKind // shared 的隔离 token 语义

    // dedicated 三件套（起 / 探 / 收）
    Launch  func(ctx, name string, port int) (authRef string, err error)
    Ready   func(ctx, name string, port int, authRef string) error
    Cleanup func(ctx, name string) error

    // shared / dedicated 额外注入的 env（由 token / authRef 派生）
    SharedEnv    func(token string) []EnvKV    // redis→REDIS_DB；milvus→MILVUS_COLLECTION_PREFIX；pg→(无)
    DedicatedEnv func(authRef string) []EnvKV  // redis→REDIS_PASSWORD；milvus/pg→(无)

    // 配额（供给前拦）
    Quota func(ctx, psID string) error          // pg→CheckDatabases+CheckDBSize；其他→dedicated 实例数上限
}

// 注册表：redis/milvus/pg 启动时注册；新 kind 仅 RegisterKind。
var kindRegistry = map[string]KindSpec{}
func RegisterKind(s KindSpec) { kindRegistry[s.Kind] = s }
```

### 4.2 供给主逻辑 strategy-generic

`supplyOne` 不再 switch kind，而是 `spec := kindRegistry[dep.Kind]` 后按 strategy 分派：

| 策略            | 通用流程（按 spec 分派）                                                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bind_existing` | `LookupBindExisting(psID, kind)` → `ConnStr` → 注入 `spec.AddrEnv`（+ authRef → password env）；token 空                                                                           |
| `shared`        | `LookupShared(kind)` → 复用判定 → 按 `spec.TokenKind` 分配 token（redis=db 号池 / milvus=前缀 / **pg=建库+role，库名即 token**）→ claim → 注入 `AddrEnv` + `spec.SharedEnv(token)` |
| `dedicated`     | 分配端口 → `spec.Launch` 起 → `spec.Ready` 探 → 登记 instance → 注入 `AddrEnv` + `spec.DedicatedEnv(authRef)`                                                                      |

**收益**：加 kafka/mysql/es = 写一个 KindSpec 注册，供给主逻辑零改动。

### 4.3 注册表

`kindRegistry` 在 `cmd/server` 装配时注册 redis / milvus / pg；`RegisterKind` 开放给未来 kind。供给主逻辑、`Reconcile`、`SetDeps`、`Cleanup` 全部通过 registry 查 spec，不再硬编码 kind 分支。

## 5. PG 收编（消除 pgsupply / mwsupply 割裂）

pg 的 KindSpec：

- **shared** = 复用 pgsupply 现有逻辑：`GetOrCreate(项目空间 PG 实例)` + 建库 `app_<id>` + role/password；库名 = token；`AddrEnv = DATABASE_URL`。配额用 pgsupply 的 `CheckDatabases` / `CheckDBSize`。
- **bind_existing**（新增）= 登记一个已有 PG（如 `yxt-pgsql`），注入 `DATABASE_URL` / `PG_*` 指向它，**不建库**（用现成库）。
- **dedicated**（新增）= `docker run` 一个独立 pgvector 容器 + 建库/role，注入 `DATABASE_URL`。

`pgsupply` 包降级为 pg-spec 的底层实现（`Launch` / `Ready` / token 分配调它），对外只暴露统一供给入口；`buildAndDeploy` 中**无条件的 `pgsupply.Provision` 调用移除**，PG 改走 `mwsupply.Reconcile`（声明才有）。

## 6. 数据模型（复用现有三张表，pg 并入）

| 表                           | 角色                                                 | pg 并入后的变化                                                                                 |
| ---------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `appdeploy_service_instance` | 一个**实例**（PG server / redis / milvus）           | 新增 pg 类型行：项目空间共享 PG / bind_existing 已有 PG / dedicated PG 容器                     |
| `appdeploy_service_binding`  | app→依赖**声明**（kind + strategy + token + status） | 新增 `kind=pg` 的声明行                                                                         |
| `appdeploy_database`         | pg 库**明细**（库名 / role / host / backup）         | **保留**，作为 pg-shared 的 token 明细：binding 的 `isolation_token` = 库名，role/password 在此 |

关系：`binding(kind=pg, shared) → service_instance(PG server) + token=db_name → appdeploy_database(该 app 的 role/password)`。pg KindSpec 的 shared-token 分配 = 建一条 `appdeploy_database` + 设 `token=库名`。**存量 pgsupply 数据天然兼容**。

## 7. 声明入口（已具备，扩展 kinds）

- **`.anp/deps.yaml`**：`services: [{kind: pg, strategy: shared}, {kind: redis, strategy: bind_existing}, ...]`；kinds 含 pg。
- **「🔗 中间件依赖」UI**：kinds 下拉加 pg；strategy 三选一（带语义说明）。
- **导入**：opencode 适配时写 deps.yaml（含 pg 声明）。
- **创建 / 开发**：UI 选 / 编码工作台改 deps.yaml。

## 8. 迁移（存量 app 无感平迁）

| 存量                                              | 处理                                                                                                                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现有 redis/milvus binding                         | **不动**（已是 binding 模型；generic 主逻辑产出相同）                                                                                                             |
| 现有自动 PG（pgsupply 给每个 managed app 建的库） | **平迁**：为每个有 `appdeploy_database` 的 app 自动补一条 `pg=shared` declared binding，指向其现有 PG 实例 + 现有库名作 token，`DATABASE_URL` 不变 → 无运行时变化 |
| `buildAndDeploy` 里的无条件 `pgsupply.Provision`  | **移除**，PG 改走 `mwsupply.Reconcile`（声明才有）                                                                                                                |
| 新应用                                            | 必须声明 pg（deps.yaml/UI）才有库——本设计批准的行为变化                                                                                                           |

平迁是一次性的（启动时 reconcile 或迁移脚本），跑完存量全部转为 declared `pg=shared`。

## 9. 配额 / dedicated 成本控制

- **pg**：沿用 `CheckDatabases`（库数）/ `CheckDBSize`（库大小）→ pg KindSpec.Quota。
- **通用化**：加一项 **dedicated 实例数 per 项目空间 上限**（redis/milvus/pg dedicated 容器合计封顶），复用 `quota.Service` 模式，防容器爆炸。
- shared 的 token 池天然有上限（redis db 号范围、milvus 前缀空间）。

## 10. 错误处理

- **best-effort，不阻塞部署**（沿用 mwsupply）；失败记 binding 的 `last_error`。
- dedicated launch 失败 → `spec.Cleanup` 回收半成品（沿用）。
- pg 建库/role 失败 → 事务式回滚（Drop database/role，沿用 pgsupply）。
- dedicated 就绪检测失败：best-effort，记 Warn 后继续 bound（容器保留，app 经 host LAN IP:port 可达；同 P3/P4 cross-network 形状）。

## 11. 测试（分层）

- **strategy-generic 主逻辑**：用 fake KindSpec **测一次**（覆盖 bind_existing/shared/dedicated 分派、token claim、env 注入、回收）——不逐 kind 重复。
- **每个 KindSpec**：单测其 `Launch` / `Ready` / token 分配 / `EnvKeys`（redis args、milvus 栈、pg 建库 SQL——多为纯函数，沿用现有 `redisRunArgs` / `milvusRunArgs` 测法）。
- **集成**：每种 kind×strategy 在 .28 跑一个 e2e（redis/milvus 已有 P1–P5；**新增 pg 的 bind_existing / shared / dedicated**）。
- **迁移**：auto-PG → declared 平迁脚本/reconcile 用 fixture 测。

## 12. 不在本期 / 未来

- 无状态依赖服务（网关/代理/sidecar）的纳入——如需要，仅暴露 `bind_existing`。
- 跨策略切换时的**数据迁移**（本期切 dedicated = 新空库，需手动导数据）。
- 更多 kind（kafka / mysql / es…）按需 RegisterKind。

## 13. 影响面（实施时触及）

- 新增：`KindSpec` 类型 + `kindRegistry` + redis/milvus/pg 三个 spec 注册。
- 重构：`mwsupply/supply.go` 的 `supplyShared` / `supplyDedicated` / `launchDedicated` / `writeSharedEnv` / `writeDedicatedEnv` 由 switch 改为 spec 分派。
- 收编：`pgsupply` 降级为 pg-spec 底层；`buildAndDeploy` 移除无条件 PG 供给。
- 数据：`appdeploy_service_instance` / `appdeploy_service_binding` 承载 pg；`appdeploy_database` 保留作 pg 库明细。
- 迁移：一次性 auto-PG → declared `pg=shared` 平迁。
- UI：「🔗 中间件依赖」kinds 加 pg。
