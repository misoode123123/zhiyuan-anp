# 依赖供给统一 P3：PG 声明化（移除自动供给 + 复用收紧 + M-2/M-3）设计

> 日期：2026-08-05 ｜ 状态：设计（待评审）｜ 上游 spec：`2026-08-04-依赖供给统一三策略-design.md`
> 相关代码：`internal/appdeploy/handler.go`、`internal/pgsupply/provisioner.go`、`internal/pgsupply/instance.go`、`internal/mwsupply/supply.go`、`internal/mwsupply/spec_pg.go`

## 1. 背景

P1（KindSpec registry 基础 + redis/milvus 迁移）+ P2a（pg shared）+ P2b（pg bind_existing + dedicated）已完成：pg 三策略齐全、声明驱动供给主逻辑就绪（`mwsupply.Reconcile` 经 KindSpec 分派）。

但 PG 仍是**双轨**：

- `mwsupply.Reconcile`（buildAndDeploy 内，`handler.go:1854-1856`）只对**声明了**的依赖供给（声明驱动）。
- `handler.go` 另有三处**无条件** `pgsupply.Provision`，不管有没有声明都给库（自动供给，旧轨）。

只要这三处还在，PG 就没真正切到声明驱动；且 P2a/P2b 评审遗留了三个小问题（复用 lag、host 耦合、空 AuthRef）。P3 收口这几件事。

## 2. 范围决策（本期明确不做）

| 项                                              | 决策     | 理由                                                              |
| ----------------------------------------------- | -------- | ----------------------------------------------------------------- |
| 存量 app 平迁（auto-PG → declared `pg=shared`） | **不做** | .28 是开发+测试库非生产；存量项目后期重新导入即可                 |
| 生产级回滚预案 / 数据保护                       | **不做** | 同上；回滚 = revert PR + 重建 backend，无数据丢失顾虑（重导兜底） |
| `pgsupply` 包对外入口收敛 / 包降级重构          | **不做** | YAGNI；pg KindSpec 已能复用 pgsupply 内部能力，无需本期收敛       |

> 即原 spec §8「平迁存量」整行移出本期；新应用「必须声明 pg 才有库」（spec §8 末行）仍是本期落地的行为变化。

## 3. 目标 / 非目标

**目标**

1. PG 切纯声明驱动：移除 `handler.go` 三处无条件 `pgsupply.Provision`。
2. 修 P2a 遗留 #2：`pgsupply.Provision` 复用收紧（只复用 `Ready`），消除 `DATABASE_URL`-lag。
3. 修 P2b 遗留 M-2：pg dedicated host 耦合。
4. 修 P2b 遗留 M-3：pg bind_existing 空 AuthRef 无守卫。
5. .28 e2e：scp 重建 backend + 真 pg 三策略（shared / bind_existing / dedicated）。

**非目标**

- 不动 redis/milvus（零行为变化）。
- 不做密码持久化（见 §5.2 备选，本期不上）。
- 不做存量数据迁移、不做 UI 默认声明 pg（新应用声明入口已具备：`PutDeps` / `.anp/deps.yaml`）。

## 4. 改动详述

### 4.1 移除无条件 PG 供给（项 1，生产行为变更）

**现状：** `handler.go` 三处对每个 managed app 无条件供给库：

| #   | 位置                   | 函数                       | 触发                                  |
| --- | ---------------------- | -------------------------- | ------------------------------------- |
| a   | `handler.go:1233-1237` | `Create`                   | 建 managed 应用后                     |
| b   | `handler.go:1408-1412` | `runImportGit/Dir`（异步） | git/目录导入，`SeedFromManifest` 之后 |
| c   | `handler.go:1526-1530` | `runImportZip`（异步）     | zip 上传导入，`SeedFromManifest` 之后 |

> 注：`buildAndDeploy`（`handler.go:1747`）本身**不**调 `pgsupply.Provision`，它走 `mwReconciler.Reconcile`（声明驱动）。自动供给全在这三处 Create/Import 入口。

**改法：** 删除这三处 `if h.provisioner != nil { h.provisioner.Provision(...) }` 块。

**改后语义：**

- 存量 app：其 `appdeploy_database` 行与 `DATABASE_URL` env 行均**保留不动**（运行时零变化）；只是不再有"创建即给库"。本期不平迁 binding，存量 app 若重新部署且未声明 pg，Reconcile 不会重供（env 行仍在，库仍可用，但平台不再纳管其 pg binding——可接受，后期重导）。
- 新建/导入 app：**不声明 pg 就没有 `DATABASE_URL`**。要库须 `PutDeps`（UI）或仓库 `.anp/deps.yaml` 声明 `pg=shared`（导入经 `SeedFromManifest` 落 declared binding，部署时 Reconcile 供给）。这是 spec §8 已批的行为变化。

**配套：** `Handler.provisioner` 字段 + `NewHandler`/`Register` 的 `provisioner *pgsupply.Provisioner` 参数**保留**——pg shared 的 KindSpec（`spec_pg.go` `SupplyShared` → `prov.Provision`）仍在用它；只是不再由 handler 直接调。装配处（`main.go`）无需改。

### 4.2 `Provision` 复用收紧（项 2，修 P2a #2）

**现状（`pgsupply/provisioner.go:54-57`）：**

```go
if existing, err := p.store.GetAppDBByApp(ctx, appID); err == nil && existing != nil &&
    (existing.Status == StatusReady || existing.Status == StatusProvisioning) {
    return existing, nil
}
```

**问题：** `Provisioning` 行是并发/中途的半成品——`DATABASE_URL` env 尚未写入（`Provision` 在 `CreateAppDB` 后、`UpsertEnv` 前就会把行落成 `Provisioning`，`SetAppDBStatus Ready` 在最后）。复用它直接 `return existing` → 调用方（`SupplyShared`）拿 `appDB.DBName` 当 token、binding 标 bound，但 app 实际没有 `DATABASE_URL`（lag）。`appdeploy_database` 不存密码，也无法事后补 DSN。

**改法：**

1. 复用条件**只留 `StatusReady`**（Ready 保证 env 已写）。
2. `Provisioning` / `Failed` 行不再早返回，落到**续供路径**：
   - 复用既有行（`existing`），不新建 `appdeploy_database`（避免 UNIQUE 冲突）。
   - 续供**复用既有行的 `DBName`/`DBRole`**（`DBName` = `app_`+随机 hex、**非**确定性派生自 appID——重算会按新名建库从而孤儿既有库，且 DSN 名与行不一致）；只生成**新密码**。
   - 库已存在则跳过 `CreateDatabase`（吞 "already exists"）；`DropRole`（若存在）→ `CreateRole`（新密码）→ `GrantAll`。
   - 重写 `DATABASE_URL` env（新 DSN）→ 翻 `Ready`。
   - 任何步骤失败 → `markFailed` + 回滚（Drop 已建 role）+ 返回错。
3. 这样既消除 lag（`Provisioning` 不再被当"已供给"），又防"卡在 `Provisioning` 永不恢复"（续供把它推进到 Ready）。

> 备选（更重，**不在本期**）：把密码/DSN 持久化进 `appdeploy_database`，失败行可直接恢复。先不上，续供已足够。

**测试：** fixture 覆盖 (a) Ready 行→原样复用不重建；(b) Provisioning 行→续供（role 重建 + env 重写 + 翻 Ready）；(c) Failed 行→续供成功；(d) 全新 app→正常建。`.28` 真 PG 验 shared。

### 4.3 修 M-2：pg dedicated host 耦合（项 3）

**现状：**

- `mwsupply/spec_pg.go` `SupplyDedicated(ctx, appID, psID, host)` 用传入的 `host`（= `r.host`，Reconciler 的 AppDeployHost）写 `service_instance.Host`。
- 但容器由 `pgsupply.InstanceManager.ProvisionDedicated`（`instance.go:92`）用 **`m.host`**（InstanceManager 的 AppDeployHost）起，`adminURL`/`dsn` 也都用 `m.host`（`instance.go:102`/`124`）。
- 两个 host 来源（`r.host` vs `m.host`）**隐式假设相等**；一旦发散，登记的 `service_instance.Host` ≠ 容器实际可达 host。

**改法（单一来源）：**

1. `PgDedicatedRunner.ProvisionDedicated` 返回值 tuple **加 `host string`**，返回它实际用的 `m.host`。
2. `spec_pg.go` `SupplyDedicated` 用**返回的 host** 填 `service_instance.Host`，不再用传入的 `host` 参数（泛型签名 `(ctx, appID, psID, host)` 不动；pg 实现内部忽略入参 host）。
3. `instance.go` `ProvisionDedicated` 返回 `m.host`。

**测试：** fake `PgDedicatedRunner` 返回指定 host → 校验登记的 `service_instance.Host` == 该返回值（而非 `r.host`）。

### 4.4 修 M-3：空 AuthRef 守卫（项 4）

**现状（`mwsupply/supply.go:129-144` bind_existing）：**

```go
connVal := ConnStr(inst)
if spec.ConnValue != nil { connVal = spec.ConnValue(inst) }   // pg → inst.AuthRef
isSecret := inst.AuthRef != ""
if err := r.env.UpsertEnv(ctx, appID, spec.AddrEnv, connVal, isSecret, "platform"); err != nil { ... }
mkBind(StatusBound, inst.ID, "", "")
```

登记的 pg bind_existing 实例若 `AuthRef`（完整 DSN）为空 → `connVal=""` → 静默写空 `DATABASE_URL=""` 且 binding 标 bound。无任何拦截。

**改法（通用空连接值守卫，零 kind 特化）：** 算出 `connVal` 后，若 `connVal == ""` → `mkBind(StatusFailed, inst.ID, "", "无可绑定的 "+dep.Kind+" 实例连接信息（AuthRef 空）")`，不写 env、直接 return。对任何 kind 的空 `ConnStr`/`ConnValue` 都成立。

**测试：** fake bind_existing 实例 `AuthRef=""` → binding failed、不写 env；`AuthRef` 非空 → 正常 bound。

## 5. 测试策略（分层）

- **单元（fake）：**
  - `pgsupply`：复用收紧 4 场景（§4.2）。
  - `mwsupply`：M-2 host 来源（§4.3）、M-3 空 AuthRef（§4.4）、bind_existing 正常路径回归。
- **回归：** `go test -p 1 ./internal/mwsupply/... ./internal/pgsupply/... ./internal/appdeploy/...` 全绿；redis/milvus 零行为变化。
- **handler 层：** 删三处 Provision 后，Create/Import 不再触发供给（可用既有 handler 测试或新增 characterization 测试确认 `provisioner` 不被调）。
- **.28 e2e（本阶段一起做）：** scp 重建 backend → 真 PG 跑 pg shared / bind_existing / dedicated 各一个；确认声明驱动端到端通、`DATABASE_URL` 正确注入、dedicated 容器可清。

## 7. 风险

- **续供的并发安全：** 同 appID 并发 `Provision`（Create 端 + 部署 Reconcile 端）仍可能；续供路径对 db 已存在做幂等（吞 already exists）、role 用 Drop+Create。无锁，但 `appdeploy_database` 的 appID 唯一约束兜底重复行。最坏双发：后到者 `DropRole`+重建，最终一致。
- **删自动供给后存量 app 体验：** 未声明 pg 的存量 app 重新部署不再被平台纳管 pg binding（库 + env 仍在，不中断）。本期接受，后期重导。
- **e2e 依赖 .28 环境：** 真 PG + scp 重建 backend；dedicated 起容器需端口/网络可达（同 P2 cross-network 形状，就绪检测 best-effort）。
