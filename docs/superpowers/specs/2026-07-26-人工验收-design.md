# 设计:测试中心 · 人工验收录入

- 日期:2026-07-26
- 模块:`platform/backend/internal/qa`、`platform/frontend/app/testing`
- 状态:待审核

## 1. 背景与目标

测试中心(`internal/qa`)目前只能**自动验收**:AI 把需求验收标准转成带 HTTP 断言的用例,对着已部署应用 URL 发请求比对,落 `passed/failed`。系统验不了的用例(无 HTTP 断言 / 需求未归属已部署应用 / 期望异常 5xx 无法触发)会被打 `manual` 标。

**问题**:`manual` 是终态占位——没有接口、没有 UI 让人把手动验证的结论录回来。用户只能在脑子里验,结果无处记录;而发布门禁(`release/handler.go`,`release_require_passed_test=true` 时要求来源需求 ≥1 条 `passed`)也就永远拿不到这些用例的贡献。

**目标**:给 `manual` 用例加"人工验收"录入——任意登录用户可录 `passed/failed` + 备注,翻 status,天然进发布门禁。

## 2. 范围与验收标准(AC)

- **AC1**:`manual` 状态用例卡片上出现"通过 / 失败 + 备注"录入控件;提交后 status 翻为 `passed`/`failed`,显示验收人、时间、备注。
- **AC2**:已人工验收的用例(`verifier_id != ''`)显示验收摘要 + "改判"按钮,改判可重录。
- **AC3**:`POST /project-spaces/:id/test-cases/:tcid/manual-verdict`:manual 或已验过 → 200 并回写;auto-only 用例 → 409;verdict 非法 → 400;用例不存在 → 404。
- **AC4**:对已人工验收的用例再点"批量验收"/"运行",不会被冲回 `manual`(后端 `RunHTTPRequest` 跳过 `verifier_id != ''` 的用例)。
- **AC5**:人工置 `passed` 的用例被 `PassedCountByRequirement` 计入,从而满足发布门禁(端到端在 .28 验:人工 passed 后,原被门禁拦截的需求可发布)。
- **AC6**:每次人工验收在 `operation_log` 留 actor(谁、何时),无需 verdict 历史子表。
- **AC7**:`manual` 卡片不再显示无意义的"▶运行"(运行只会重盖 manual)。

## 3. 非目标(YAGNI)

- 不做证据附件上传(截图/日志)。
- 不做 verdict 改判历史子表(靠 `operation_log` 操作级审计兜底)。
- 不做用例指派(assignee)机制。
- 不允许对 auto-only 用例(draft/passed/failed/partial 且无 verifier)人工覆盖结论。

## 4. 数据模型

### 4.1 迁移 `000019_test_case_manual_verdict`

- up:
  ```sql
  ALTER TABLE test_case
    ADD COLUMN manual_note TEXT DEFAULT '',
    ADD COLUMN verifier_id  TEXT DEFAULT '',
    ADD COLUMN verified_at  TIMESTAMPTZ;
  ```
- down: `ALTER TABLE test_case DROP COLUMN verified_at, DROP COLUMN verifier_id, DROP COLUMN manual_note;`

### 4.2 `TestCase` 结构体(`internal/qa/model.go`)

新增字段:

```go
ManualNote string     `json:"manual_note,omitempty" db:"manual_note"`
VerifierID string     `json:"verifier_id,omitempty" db:"verifier_id"`
VerifiedAt *time.Time `json:"verified_at,omitempty" db:"verified_at"`
VerifierName string   `json:"verifier_name,omitempty" db:"verifier_name"` // join 出来,非表列
```

`status` 枚举不变:`draft / passed / failed / manual / partial`。是否"人工验过"以 `verifier_id != ''` 判。

### 4.3 `tcCols` 与查询 join(`internal/qa/store.go`)

- `tcCols` 各列加 `t.` 前缀,末尾追加 `, COALESCE(ver.name,'') AS verifier_name`。
- 三处查询(Get / ListByProjectSpace / ListByRequirement)统一改为:
  ```sql
  SELECT <tcCols> FROM test_case t
  LEFT JOIN "user" ver ON ver.id = t.verifier_id
  WHERE ... ORDER BY ...
  ```
- **Store 不 import `auth` 包**,直接 SQL 引用 `"user"` 表(避免循环依赖);Handler 仍 import `auth` 取 `CtxUserDBID` 常量(`auth` 不依赖 `qa`,无循环——`performance/handler.go` 已是此模式)。

## 5. API

### 5.1 路由(`internal/qa/handler.go` Register)

新增:

```go
r.POST("/project-spaces/:id/test-cases/:tcid/manual-verdict", h.ManualVerdict)
```

鉴权继承 v1 组(`AuthUser` + `AutoRequire` + `audit.Middleware`),任意登录用户可调。

### 5.2 `Handler.ManualVerdict`

请求体:`{ "verdict": "passed"|"failed", "note": string }`

1. 取 tc,`id` 空 → 404 (40402)。
2. 校验 `verdict ∈ {passed, failed}`,否则 400 (40001)。
3. **范围守卫**:仅当 `tc.Status == "manual"` 或 `tc.VerifierID != ""` 放行;否则 409 (40902,"该用例非人工验收范围(仅 manual 用例支持人工验收)")。
4. 调 `svc.RecordManualVerdict(ctx, tc, verdict, note, verifierID)`,其中 `verifierID = c.GetString(auth.CtxUserDBID)`。
5. **re-`Get` 回填**:`UpdateManualVerdict` 不写 join 列,返回前用 `svc.GetCase` 重取一次,使响应带 `verifier_name`(前端虽 reload,但响应自洽更稳)。
6. 返回更新后的 tc。

### 5.3 `Service.RecordManualVerdict`

```go
func (s *Service) RecordManualVerdict(ctx, tc *TestCase, verdict, note, verifierID string) error
```

- 置 `tc.Status = verdict`、`tc.ManualNote = note`、`tc.VerifierID = verifierID`、`tc.VerifiedAt = nowTime()`。
- 调 `store.UpdateManualVerdict(ctx, tc)`。

### 5.4 `Store.UpdateManualVerdict`

```go
func (s *Store) UpdateManualVerdict(ctx, tc *TestCase) error {
  _, err := s.db.ExecContext(ctx,
    `UPDATE test_case SET status=$1, manual_note=$2, verifier_id=$3, verified_at=$4 WHERE id=$5`,
    tc.Status, tc.ManualNote, tc.VerifierID, tc.VerifiedAt, tc.ID)
  return err
}
```

单独方法,不复用 `UpdateRun`(职责不同:`UpdateRun` 回写 HTTP 运行结果,不写验收三列)。

## 6. 防冲掉(AC4)

`Service.RunHTTPRequest` 开头新增:

```go
if tc.VerifierID != "" {
    return nil // 已人工验收,自动运行不再覆盖
}
```

对单条 `Run` 和批量 `RunForReq` 同时生效(两者都走 `RunHTTPRequest`)。

## 7. 前端(`platform/frontend/app/testing/page.tsx`)

按卡片状态分支(`hasHTTP`、`status`、`verifier_id` 三者驱动):

- `status === 'manual'`:渲染**人工验收控件**替代「▶运行」:
  - 备注输入框(可选)+「✓ 通过」「✗ 失败」两按钮。
  - 提交 → `POST .../test-cases/:tcid/manual-verdict` → reload 列表。
- `verifier_id`(已人工验收):渲染验收摘要徽标(✓通过/✗失败 + verifier_name + verified_at + 备注)+「改判」按钮;「改判」展开同上录入控件。不显示「▶运行」。
- 其它(auto-only:draft/passed/failed/partial 且无 verifier):维持现状的「▶运行」。

新增本地 state:`verdictID`(正在提交的 tcid)、`editVerdictTC`(展开改判的 tcid)、`note` 文本。

> 前端 Next.js 注意:`platform/frontend/AGENTS.md` 明确"这不是你熟悉的 Next.js",写前端代码前先读 `node_modules/next/dist/docs/` 相关指南。

## 8. 鉴权与审计

- 鉴权:v1 组,任意登录用户,无额外 admin 守卫(Q2 决定)。
- 审计:`audit.Middleware` 自动落每次 POST,`operation_log.actor_id` = `CtxUserDBID`(绩效那轮已铺)。这是不做 verdict 历史子表的依据。

## 9. 测试(TDD)

按"前后端交叉验证"纪律(memory),测试 + 真驱动前端打后端。

- **门禁回归**:人工 passed 用例被 `PassedCountByRequirement` 计入(进发布门禁)。
- **端到端(.28)**:scp 部署,前端真打:manual 用例录通过 → 卡片变绿显验收人 → 该需求发布门禁放行。

## 10. 顺带

发布门禁提示文案(`release/handler.go:90`)补"或对 manual 用例做人工验收",让用户知道这条路。

## 11. 风险与回退

- 迁移可 down(仅 drop 3 列)。
- 后端范围守卫是强约束:即使前端误传,auto-only 用例也不会被人工覆盖。
- 若验收人显示名 join 影响性能(用例量极大),可降级为只返 `verifier_id`;当前量级无虑。
