# 应用部署拓扑图 设计

> 日期：2026-08-05 ｜ 状态：设计（待评审）
> 相关代码：`platform/frontend/app/applications/page.tsx`、`platform/frontend/lib/`、后端 `platform/backend/internal/appdeploy/`（不改）

## 1. 背景

应用部署界面（`/applications`）每个应用卡片当前用文字+徽章分散展示：test/prod 环境卡（url/status/host_port）、依赖区（kind/strategy/status/token）、网络模式、节点。**缺一张「这个应用部署后内部长什么样」的图**——看不到应用容器与其依赖的中间件容器（redis/milvus/pg）之间的连接关系、注入的 env、各自跑在哪。

本特性给每个已部署应用加一张**手绘盒+箭头拓扑图**：应用容器层 → 标注 env 变量名的边 → 中间件实例层。纯前端，从既有接口数据客户端拼装，零后端改动、零新依赖。

## 2. 目标 / 非目标

**目标**

1. 已部署应用（≥1 个 test/prod 实例）渲染一张拓扑：应用容器盒（每个已部署 env 一个）+ 中间件依赖实例盒（按 kind）+ 标 env 变量名的连接边。
2. 复用既有数据（`app.instances` + `deps` + `catalog.instances`），无新接口、无后端改动。
3. 拓扑拼装逻辑（kind→envLabel、dep→实例 host、按 env 取应用盒）抽 `lib/topology.ts` 纯函数 + vitest 覆盖（沿用 `deps-ui.ts` 范式）。

**非目标**

- **未部署应用不画**：应用无任何 instance（未部署）时不渲染拓扑区（不画虚线占位盒）。
- **不引入图库**：用手绘 div/SVG 盒+箭头（本前端零图库，YAGNI；每应用结构固定且小，手绘够用）。不做拖拽/缩放/自动布局。
- **不做全局容器图**：只画**单个应用内部**结构，不做跨应用/节点级拓扑。
- **不改后端**。
- **external 应用不渲染**（同 `DepsSection`：external 无容器、不经 Reconcile 供给）。

## 3. 关键决策

| 决策       | 选定                                                        | 理由                                                                |
| ---------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| 可视化形态 | **手绘盒+箭头（两层）**                                     | 零新依赖；两层布局（应用层→中间件层）避 2×N 交叉连线，清晰且易手绘  |
| 多 env     | **test+prod 两个应用盒同图**（依赖是 app 级、共享）         | 用户决：两个都画，信息全                                            |
| 边标签     | **真实 env 变量名**（DATABASE_URL/REDIS_ADDR/MILVUS_ADDR）  | 用户决：贴近实际注入，开发者一眼对应代码                            |
| 未部署态   | **不画**（无 instance 即不渲染整块）                        | 用户决：只看已部署实际结构                                          |
| 数据来源   | **客户端拼装既有接口**                                      | `app.instances`+`deps`+`catalog.instances` 已含全部所需；无后端改动 |
| host 取值  | 从 `instance.url`/`host_port` 派生（不依赖 node_id）        | app 的部署节点未必持久化在 instance 上；url 内嵌 host 足够标注      |
| 测试落点   | 拼装纯函数抽 `lib/topology.ts`+vitest；组件靠 tsc+build+e2e | 沿用 `deps-ui.ts`/`devstep.ts` 范式（vitest 仅纯函数/node env）     |

## 4. 改动详述

### 4.1 新增 `lib/topology.ts`（纯函数）

```ts
import type { CatalogInstance, Dep } from "./deps-ui";

// kind → 注入的 env 变量名（mwsupply 注入源，单源 map；新增 kind 同步此处）。
export const KIND_ENV_LABEL: Record<string, string> = {
  pg: "DATABASE_URL",
  redis: "REDIS_ADDR",
  milvus: "MILVUS_ADDR",
};

export function kindEnvLabel(kind: string): string {
  return KIND_ENV_LABEL[kind] ?? kind.toUpperCase() + "_ADDR";
}

// 应用容器盒（每个已部署 env 一个）。
export type AppBox = {
  env: string; // test / prod
  status: string; // running / building / failed / stopped ...
  host: string; // 从 url 派生（无 url 则空）
  port: number; // host_port
  version: number;
  image: string;
};

// 从 app.instances 派生应用盒（仅含已部署 env；按 env 排序 test 前 prod 后）。
export function appBoxes(
  instances:
    | {
        env: string;
        status: string;
        url: string;
        host_port: number;
        version: number;
        image?: string;
      }[]
    | undefined
): AppBox[];

// 中间件依赖实例盒。
export type DepBox = {
  kind: string;
  strategy: string; // shared / bind_existing / dedicated
  status: string; // bound / declared / failed
  envLabel: string; // kindEnvLabel(kind)
  host: string; // 解析到的实例 host（bound 时从 catalog；无则空）
  port: number;
  name: string; // 实例名（bound 时）
  error: string; // failed 时的 last_error
};

// 由 deps + catalog 拼依赖盒：dep.instance(id) 交叉引用 catalog.instances 取 host/port/name。
// bound → 有实例信息；declared/failed → host/port 空盒（failed 带 error）。
export function buildDepBoxes(deps: Dep[], instances: CatalogInstance[]): DepBox[];
```

`url`→`host` 解析：`new URL(url).host` 拆出 host（失败兜底空串）。env 排序：定义 `["test","prod"]` 顺序，未列 env 排末。

### 4.2 新增 `TopologySection` 内联组件（`applications/page.tsx`）

与 `DepsSection`/`ArtifactSection` 同级（置于依赖区下方）。props：`{ psID, appID, app }`——`app`（父级 `apps` state 已持有，含 `instances`/`name`/`app_kind`/`network_mode`）提供应用盒数据；`deps`+`catalog` 按 §4.3 方案 (a) 在组件内自 fetch（同 `DepsSection` 范式）。

**渲染条件**：`app.deploy_mode !== "external" && app.instances?.length > 0`（已部署才画）。

**布局（两层）**：

```
┌─ 应用容器 ─────────────────────────────┐
│  [myapp·test :9100 v2 running]          │
│  [myapp·prod :9200 v3 running]          │
└─────────────────┬───────────────────────┘
        DATABASE_URL │ REDIS_ADDR │ MILVUS_ADDR
┌─────────────────┴───────────────────────┐
│ [pg :5432 shared·bound] [redis :6379 bind·bound] [milvus :19530 dedicated·failed] │
└─ 中间件依赖 ─────────────────────────────┘
```

- 应用层：`appBoxes(app.instances)` 每盒显示 `name·env :port vN status`，status 用既有颜色 token（running=success / building=warn / failed=danger / stopped=accent）。
- 连接区：从应用层下行到中间件层，每条边标对应 kind 的 `kindEnvLabel`（真实变量名）。用 SVG 折线或简化为「↓ DATABASE_URL」标签列（实现择一，响应式优先）。
- 中间件层：`buildDepBoxes(deps, catalog.instances)` 每盒显示 `kind :port strategy·status`，status 颜色同上；failed 盒附 `error`（截断）；无依赖时该层显「无中间件依赖」。

### 4.3 接线

`ApplicationsPage` 应用卡片里，在现有 `<DepsSection>` 之后加：

```tsx
{
  a.deploy_mode !== "external" && a.instances && a.instances.length > 0 && (
    <TopologySection psID={psID} appID={a.id} app={a} />
  );
}
```

**数据来源**：`deps`/`catalog` 当前由 `DepsSection` 各自 fetch（自包含组件，数据不外露）。两种接法（计划阶段定）：

- (a) `TopologySection` 也自包含 fetch（同 `DepsSection`，`Promise.all` 拉 deps+catalog）——简单、与既有范式一致，代价是同一应用多一次重复 fetch；
- (b) 把 deps/catalog 提到 `ApplicationsPage` 级 state 下发给两个子组件——省重复 fetch，但改 `DepsSection` 接口（侵入大）。
- **倾向 (a)**（自包含 fetch），与 `DepsSection`/`ArtifactSection` 范式一致、改动面小；同一应用两个子组件各 fetch 一次 catalog/deps 的代价可接受（已是 best-effort、页面本就轮询）。

### 4.4 行为

- 应用未部署（无 instance）→ 不渲染拓扑区。
- 仅 test 部署 → 只画 test 应用盒（不画 prod 占位）。
- 依赖 bound → 中间件盒带 host:port；declared/failed → host:port 空、按 status 着色、failed 附 error。
- external 应用 → 不渲染（同 DepsSection）。
- 无新 API；复用 `GET .../apps/:id/detail`（instances）、`GET .../apps/:id/deps`、`GET .../deps/catalog`。

## 5. 测试策略（沿用既有模式）

- **纯函数单测**（`lib/topology.test.ts`，vitest node env）：
  - `kindEnvLabel`：pg/redis/milvus 命中 map；未知 kind 兜底 `KIND_ADDR`。
  - `appBoxes`：多 env 派生 + test-before-prod 排序；url→host 解析（含异常 url 兜底空串）；空 instances → `[]`。
  - `buildDepBoxes`：bound dep 交叉引用 catalog 取 host/port/name；declared/failed dep host 空；failed 带 error；dep.instance 找不到 catalog 项时不崩（空 host）。
- **组件**：无 vitest（vitest 仅纯函数）；靠 `tsc --noEmit` + `next build` + .28 手动 e2e。
- **.28 手动 e2e**：已部署应用见拓扑（应用盒+中间件盒+env 标签边）；仅 test 部署只画 test 盒；failed 依赖盒带 error；未部署应用无拓扑区；external 应用无拓扑区。

## 7. 风险

- **重复 fetch**：倾向 (a) 自包含 fetch，`TopologySection` 与 `DepsSection` 各拉一次 catalog/deps；best-effort、页面本就 3s 轮询，代价可接受。若担心可后续提 state 共享。
- **url→host 解析**：`new URL` 对异常 url 抛错 → try/catch 兜底空串（不崩）。
- **dep.instance 找不到 catalog 项**：buildDepBoxes 返回空 host 盒（不崩；bound 但 catalog 暂缺时降级显示）。
- **两层连线响应式**：窄屏下 env 标签列可能挤；实现时用 flex-wrap + 简化箭头，优先信息可读而非像素级对齐。
- **分支**：本特性依赖 P5 的 `lib/deps-ui.ts`（import `Dep`/`CatalogInstance`），须在 P5（PR #3）合入后或同分支上做；分支策略（并入 PR #3 vs 新 PR）由用户定。
