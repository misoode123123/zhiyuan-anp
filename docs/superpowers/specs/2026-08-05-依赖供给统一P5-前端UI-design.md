# 依赖供给统一 P5：前端 UI（pg 选择 + 实例展示 + dedicated 配额维度）设计

> 日期：2026-08-05 ｜ 状态：设计（待评审）｜ 上游 spec：`2026-08-04-依赖供给统一三策略-design.md`、`2026-08-05-依赖供给统一P3-pg声明化-design.md`、`2026-08-05-依赖供给统一P4-dedicated配额-design.md`
> 相关代码：`platform/frontend/app/applications/page.tsx`（`DepsSection`）、`platform/frontend/app/quota/page.tsx`、`platform/frontend/lib/`、后端 `platform/backend/internal/mwsupply/supply.go`（`DepsCatalog`）

## 1. 背景

P1–P4 完成依赖供给统一的后端：KindSpec 注册表收编 redis/milvus/pg 三策略（shared/bind_existing/dedicated）+ pg 声明化 + dedicated 实例数配额第 5 维。**后端 API 已全部就绪并经 .28 e2e 验证**，前端却滞后两处：

1. **依赖选择器**（`applications/page.tsx` 的 `DepsSection`）：kind/strategy 下拉是 catalog 驱动，pg 实际已能选出（`DepsCatalog.Kinds=["redis","milvus","pg"]`，supply.go:473）；但 `catalog.instances` 被 fetch 后**从未渲染**——用户看不到部署机上有哪些可绑定实例（含 pg）。这是 P2a 遗留 Minor #5（「DepsCatalog pg no instances → P2b(UX)」）。
2. **配额看板**（`quota/page.tsx`）：P4 后端加了第 5 维 `max_dedicated_instances` / `used_dedicated_instances`，前端仍只展示 4 维（应用数/库数/库总大小/每日 AI 调用），dedicated 实例数配额对用户不可见。

P5 收尾前端：让 pg 在依赖选择器可见可选、可绑定实例（含 pg）可见、dedicated 配额维度可见可配。

## 2. 目标 / 非目标

**目标**

1. `DepsSection` 渲染只读「可绑定实例」清单（`catalog.instances`，按 kind 分组，含 pg），让用户知道 bind_existing 会绑到什么。
2. `DepsSection` 编辑态：当某依赖 `strategy=bind_existing` 时，高亮该 kind 的实例组（提示「将绑定此类实例」）。
3. `QuotaPage` 加第 5 维 dedicated 实例数（卡片 + admin 编辑），与 P4 后端字段对齐。
4. 新增逻辑以纯函数抽到 `lib/` 并用 vitest 覆盖（沿用 `devstep.ts`↔`devstep.test.ts` 范式）。

**非目标**

- **不做实例选择器**：后端声明只有 `{kind, strategy}`、无 per-declaration instance 字段，bind_existing 在供给时按 kind 隐式匹配实例（`DeclareBinding(appID, psID, kind, strategy)`）。做选择器需同步改后端（PutDeps/DepDeclaration/supply 解析），超出「后端已就绪」范围，P5 不碰。
- **不做 per-kind 策略过滤**：三策略对 redis/milvus/pg 统一（supply.go:474-478），下拉按 catalog 原样渲染，不给 pg 特例。
- **不做组件测试基建**：前端 vitest 当前是纯函数/node env（无 jsdom/RTL），P5 不引入组件测试依赖。
- **不改后端**：四类 API（`GET /deps/catalog`、`PUT /deps`、`GET /deps`、`PUT/GET /project-spaces/:id/quota`）均已就绪，P5 纯前端。

## 3. 关键决策

| 决策         | 选定                                                                                            | 理由                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 实例展示形态 | **只读清单 + 编辑态高亮（标记不裁剪）**                                                         | 契约无 instance 字段，只能只读；高亮同 kind 组提示用户 bind_existing 的去向，不裁剪保持信息完整 |
| pg 在选择器  | catalog 驱动，**已可见，仅验证**                                                                | `Kinds` 已含 pg（supply.go:473），下拉无需改；统一对待，不加 pg 特例                            |
| 测试落点     | **deps 逻辑抽 `lib/` 纯函数 + vitest；quota 靠 TS 类型 + build + e2e**                          | deps 分组/过滤有分支值得单测；quota 第 5 维是声明式数据（加 DIMENSIONS 条目），强行抽函数会造作 |
| 类型归属     | deps 相关类型（`Dep`/`DepsCatalog`/`CatalogInstance`）从 page.tsx 内联**提到 `lib/deps-ui.ts`** | 顺带治类型内联重复；新纯函数需引用这些类型，就近定义；控制改动面（只提 deps 相关）              |
| 验证门槛     | 沿用既有模式：vitest 单测 + `build` + .28 手动 e2e                                              | 与 P1–P4 一致（subagent-driven + 每 task 评审 + .28 终验）                                      |

## 4. 改动详述

### 4.1 新增 `lib/deps-ui.ts`（纯函数 + 类型）

把 `applications/page.tsx` 内联的 deps 相关类型提到此文件，并新增分组/过滤纯函数：

```ts
// 依赖声明（后端 appdeploy.DepDeclaration）：kind/strategy 用户编，status/instance/token 供给结果。
export type Dep = {
  kind: string;
  strategy: string;
  status: string;
  instance?: string;
  token?: string;
  error?: string;
};

// catalog 实例（后端 appdeploy.CatalogInstance）。
export type CatalogInstance = {
  id: string;
  kind: string;
  name: string;
  supply_mode: string;
  host: string;
  port: number;
};

// 依赖勾选器 catalog（后端 appdeploy.DepsCatalog）。
export type DepsCatalog = {
  kinds: string[];
  strategies: { name: string; desc: string }[];
  instances: CatalogInstance[];
};

// groupInstancesByKind 按 kind 分组实例，保持 catalog 出现顺序（Map 保插入序）。
// UI 只读清单用：每组渲染一个 kind 区块。
export function groupInstancesByKind(instances: CatalogInstance[]): Map<string, CatalogInstance[]>;

// filterInstancesByKind 返回指定 kind 的实例（编辑态高亮该 kind 组用）。
// kind 缺失/无匹配 → 空数组（不抛）。
export function filterInstancesByKind(
  instances: CatalogInstance[],
  kind: string
): CatalogInstance[];
```

`applications/page.tsx` 删除内联的 `Dep` / `DepsCatalog`（及 `CatalogInstance`——当前内联在 `DepsCatalog.instances` 元类型里），改为 `import type { Dep, DepsCatalog, CatalogInstance } from "@/lib/deps-ui"`。

### 4.2 `DepsSection` 改动（`applications/page.tsx`）

**只读「可绑定实例」面板**：在依赖列表（`list.map`）之后、「+ 添加依赖」按钮之前，加一块。仅当 `catalog?.instances?.length` 非空时渲染：

```tsx
{
  catalog && catalog.instances.length > 0 && (
    <InstancesPanel instances={catalog.instances} highlightKinds={highlightKinds} />
  );
}
```

- `InstancesPanel`（同文件内联组件，仿 `ArtifactSection`/`NetworkModeSection` 范式）：用 `groupInstancesByKind` 分组，每组标题 = kind（含 pg），列 `name · host:port · supply_mode`。组标题 kind 命中 `highlightKinds` → 加边框/底色 + 提示「将绑定此类实例」。

**编辑态高亮逻辑**（在 `DepsSection` 内派生，传给 `InstancesPanel`）：bind_existing 可能同时对**多个 kind** 声明，故高亮目标用 `Set<string>` 而非单值：

```ts
// 非编辑态（editingDeps=null）→ 空 Set，全不高亮；
// 编辑态 → 收集所有 strategy=bind_existing 的 kind。
const highlightKinds = new Set(
  (editingDeps ?? []).filter((d) => d.strategy === "bind_existing").map((d) => d.kind)
);
```

**kind 下拉 / strategy 下拉 / saveDeps**：**不改**。pg 已在 `catalog.kinds`，下拉自动含；`saveDeps` 仍发 `{kind, strategy}` 裸数组（契约不变）。新增依赖默认 strategy 仍 `strategies[0].name=bind_existing`（统一对待）。

**external 应用**：`DepsSection` 已仅在 `deploy_mode !== "external"` 时渲染（page.tsx:1867），实例面板随依赖区一同不渲染，无需额外处理。

### 4.3 `QuotaPage` 改动（`quota/page.tsx`）

页面已是 `DIMENSIONS` 数据驱动（卡片 + 编辑表单都 `map` `DIMENSIONS`），第 5 维近乎免费：

- `Quota` 类型加 `max_dedicated_instances: number`。
- `Usage` 类型加 `used_dedicated_instances: number`。
- `DIMENSIONS` 加一项：

```ts
{
  key: "max_dedicated_instances",
  label: "专属实例数",
  unit: "个",
  icon: "🖥️",
  usedKey: "used_dedicated_instances",
},
```

- `form` state 加 `max_dedicated_instances: 0`；`load` 回填 `r.data.quota.max_dedicated_instances`。
- `save` body：`form` 整体 JSON.stringify（已含新字段），后端 `*int` 区分未改字段，全传安全（与 P4 handler `MaxDedicatedInstances *int` 对齐）。
- 文案：卡片上方说明「4 维度强制」→「**5** 维度强制：应用数 / 库数 / 库总大小 / 每日 AI 调用 / **专属实例数**」；`DIMENSIONS` 上方注释同步。

`DIMENSIONS` 的 `Dim` 类型 `key`/`usedKey` 联合需补 `"max_dedicated_instances"` / `"used_dedicated_instances"`（TS 强校验，遗漏即编译失败）。

### 4.4 行为

- **依赖页**：进入应用 → 依赖区下方见「可绑定实例」清单（redis/milvus/pg 分组）；点「编辑」把某依赖 strategy 选 bind_existing → 对应 kind 实例组高亮；保存后高亮随退出编辑态消失。无实例时面板不渲染（不显空态噪音）。
- **配额页**：多一张「专属实例数」卡片（`used / max` + 进度条 + 满/接近上限提示）；admin 编辑表单多一行「🖥️ 专属实例数上限」；保存回显。
- **无新 API 调用**：均复用既有 `GET .../deps/catalog`、`GET .../deps`、`GET/PUT .../quota`。

## 5. 测试策略（分层，沿用既有模式）

- **纯函数单测**（`lib/deps-ui.test.ts`，vitest node env）：
  - `groupInstancesByKind`：多 kind 混合（redis+pg+milvus）分组正确；保序；空数组 → 空 Map；同 kind 多实例归同组。
  - `filterInstancesByKind`：命中 kind 返回其全部实例；不命中 kind → `[]`；空 instances → `[]`。
- **quota**：第 5 维是声明式数据（加 `DIMENSIONS` 条目 + 类型字段），无可抽纯函数分支；靠 **TS 类型强校验（`Dim` 联合补字段，遗漏编译失败）+ `next build` + .28 e2e** 覆盖，不强行造作单测（诚实标注）。
- **构建**：`pnpm --filter frontend build` 过（tsc + Next 构建，类型扩展的强校验兜底）。
- **回归**：`pnpm --filter frontend test` 既有 `lib/*.test.ts` 全绿。
- **.28 手动 e2e**：admin 登录 → ① 应用页依赖区下拉见 pg；注册一个 pg 实例（DB 直插或既有实例）后刷新，实例清单见 pg 组 + host:port；编辑选 bind_existing → pg 组高亮。② 配额页见第 5 维卡片 + 改 `max_dedicated_instances` 保存回显 + `used` 随 dedicated 部署变化。

## 7. 风险

- **类型迁移波及**：把 `Dep`/`DepsCatalog` 从 page.tsx 内联提到 `lib/deps-ui.ts`，page.tsx 内所有引用改 import；TS 编译强校验兜底，零遗漏。`Envelope`/`App`/`Instance` 等非 deps 类型**不动**（控制改动面）。
- **高亮多 kind 语义**：bind_existing 可同时对多 kind 声明 → 高亮目标用 `Set<string>` 而非单值；实现时勿漏多选情形。
- **catalog.instances 来源**：来自后端 `ListActiveInstances`（kind 无差别返所有 active 实例），pg 实例需先注册才出现（注册走 mw-instances API，有 admin role 门禁 40301，pre-existing 非 P5）；.28 e2e 用既有/DB 直插实例验证展示，不验证注册流程。
- **quota `*int` 全传**：`save` 全传 form（含未改字段），后端 `*int` + `validate:omitempty` 区分；与 P4 handler 契约一致，已 e2e 验证（code 0）。
- **纯前端、无后端风险**：不碰后端，无迁移/无 API 契约变更；唯一外部依赖是既有四类 API 的响应字段（已就绪）。
