## 1. 背景与问题

ANP 平台托管的「产出应用」（由 AI 编码 + `appdeploy` 引擎构建部署）当前是**散落的单 docker 容器**：

- 每个应用 = `docker run -d` 单容器，端口直接映射宿主：test `9100-9199` / prod `9200-9300`
- 应用访问是 `http://10.10.0.28:9xxx` **直连裸端口**
- 应用的数据库靠 `-e KEY=VALUE` 各自注入、各自为政；平台不供给、不备份、不管迁移
- nginx(8088) 只反代平台三件套（前端/backend/agent-runtime），**不代理应用流量**

### 三个核心痛点

| #   | 痛点                                     | 后果                                              |
| --- | ---------------------------------------- | ------------------------------------------------- |
| 1   | 应用**数据库**无统一供给/隔离/备份       | 应用各自搞 DB，平台无法集中备份、迁移、监控、配额 |
| 2   | 应用 **API** 无统一入口/鉴权/可观测      | 端口裸露、无统一鉴权、无监控、URL 混乱            |
| 3   | **平台级 / 项目级 / 应用级**三层边界不清 | 管控逻辑和数据归属混乱，扩展困难                  |

平台已有良好基础：一个 PG（pgvector）库装所有平台数据、20 个模块表带 `project_space_id`、`capability/Gateway` 已是「应用→平台 AI」方向的调用网关（APIKey 鉴权 + 计量）。本设计把这些零散能力收敛为**统一的应用库 + 应用 API 管控面**。

## 2. 目标与关键决策

### 核心原则

> **平台有平台库（`anp`），应用有应用库（`app_<id>`）；应用库必须在平台注册，由平台统一供给与管理。平台管「库容器与基础设施」，应用管「库里的业务表」。**

### 五个已锁定决策

| 维度        | 选择                                                                           | 理由                                                                            |
| ----------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 应用形态    | 多数独立，少数借平台能力协作                                                   | 应用默认强隔离，能力调用走 capability 网关                                      |
| 数据库供给  | **平台统一供给 PG**（应用 docker 不含 DB，只连 `DATABASE_URL`）                | 收口到 PG，才能集中备份/迁移/隔离/配额；应用表结构仍由应用自己开发              |
| DB 隔离粒度 | **每应用一个独立库（database-per-app）**                                       | 隔离最强，单应用独立备份/恢复/配额，故障不蔓延                                  |
| API 入口    | **平台网关统一代理 + 保留内网直连**                                            | 对外统一域名/鉴权/TLS/计量，内网调试保留直连                                    |
| 扩展性      | **每项目一个独立 PG 实例（无 pgbouncer）**；多机用 docker swarm 过渡，不上 K8s | 按项目隔离 + 可独立部署；直连无兼容坑；加项目实例即扩；K8s 留待真正需弹性伸缩时 |

## 3. 总体架构：三层模型 + 两大贯穿基础设施

```
                          ┌──────────────────────────────────┐
  外部用户/调用方 ───────▶ │  入口 nginx(8088)                  │
                          │   /api/   → backend(平台API)       │
                          │   /apps/  → appgw(应用网关) ──┐    │  统一鉴权/路由/TLS/计量/可观测
                          │   /agent/ → agent-runtime     │    │
                          └───────────────────────────────┼────┘
                                                          │
   ┌──────────────────────────────────────────────────────┴─────────────────────┐
   │                       平台层（管控面 · anp 库）                               │
   │  身份/RBAC · project_space · appdeploy_application(应用注册表) · capability   │
   │  ★pgsupply(库供给) · ★appdeploy_route(路由表) · ★project_quota(配额)          │
   │  计量计费 · 可观测聚合 · 审计                                                 │
   ├──────────────────────────────────────────────────────────────────────────────┤
   │                       项目层（逻辑聚合 · anp库内 project_space_id）            │
   │  成员/角色 · 配额(应用数/库数/库大小/调用量) · 项目级密钥配置 · 聚合视图        │
   │  （不落物理库边界，纯管控面）                                                 │
   ├──────────────────────────────────────────────────────────────────────────────┤
   │                       应用层（运行时 · 单docker + 独立库）                     │
   │  app_<id> 库(业务表,平台不碰) · 内网端口直连(调试) · 持APIKey调capability       │
   └──────────────────────────────────────────────────────────────────────────────┘
         两大基础设施贯穿三层：
         ① PG 供给（pgsupply）：每项目独立 PG 实例 + 应用 database + 专用 role + 注入连接串 + 集中备份
         ② API 网关（appgw）：所有应用对外流量统一入口，鉴权/路由/计量/可观测
```

## 4. 三层边界定义（核心问题正面回答）

### 🟦 平台级（全局唯一，存 `anp` 库；不带 `project_space_id` 或全局生效的部分）

- 身份与权限（`user` / `role` / RBAC，已有 `auth`）
- 项目空间注册（`project_space`，已有）
- **应用注册表**（`appdeploy_application`，已有，复用）
- **PG 供给器**（`pgsupply`，新增）：建库 / 建 role / 发连接串 / 备份调度
- **路由表**（`appdeploy_route`，新增）：appcode → upstream 映射，供 appgw 消费
- **配额定义**（`project_quota`，新增）：每项目资源上限
- capability 能力市场 + 用量计费（已有 `capability`）
- 部署引擎（已有 `appdeploy`）
- 可观测聚合（日志/指标/trace）、审计日志

> **判据：建库 / 建账号 / 发路由 / 全局身份 = 平台级。**

### 🟩 项目级（`anp` 库内带 `project_space_id`，逻辑边界不是物理边界）

- 成员与角色：谁能看 / 操作这个项目（已有 `membership`）
- 配额：最多几个应用、几个库、库总大小、capability 调用量（新增 `project_quota`）
- 项目级密钥 / 配置：项目下应用共用的配置
- 聚合视图：这个项目下所有应用、用量、健康度

> **判据：谁能用多少、谁能看哪些 = 项目级。**

### 🟨 应用级（每个应用自己的 `app_<id>` 库 + 容器，平台不碰业务表）

- 应用业务数据（平台不读不写）
- 应用运行时配置 / 密钥（作为 `-e` 注入容器，含平台供给的 `DATABASE_URL`）
- 应用业务表的 schema / migrations（应用自带，平台只触发）
- 应用自己的内部用户体系（可选，叠加在平台身份之上）

> **判据：库里装什么表、表里存什么业务数据 = 应用级。**

**一句话总纲**：

> 建库 / 发路由 = 平台级；能用多少 / 谁能用 = 项目级；库里装什么 = 应用级。

## 5. 应用数据库统一管理

### 5.1 生命周期闭环（平台全托管）

```
  创建应用 ──▶ ① 注册       appdeploy_application 登记（已有，复用）
                ② 供给       pgsupply 建 app_<shortid> 库 + 专用 role(仅本库) + 生成连接串
                ③ 纳管登记   appdeploy_database 写库元数据；DATABASE_URL 写入 appdeploy_env
  ────────────────────────────────────────────────────────────────────────
  发布部署 ──▶ ④ 注入       appdeploy EnvPairs() 已含 DATABASE_URL → docker run -e（零改造）
                ⑤ 迁移触发   平台对该 app 库触发应用自带 migrations，记录 schema_version
                ⑥ 路由生效   写 appdeploy_route，appgw /apps/<code>/ 即时可达
  ────────────────────────────────────────────────────────────────────────
  运行期间 ──▶ ⑦ 统一管理    备份 / 监控 / 迁移版本 / 配额 / 连接管理
  ────────────────────────────────────────────────────────────────────────
  删除应用 ──▶ ⑧ 归档/清理  归档 app_<id> 库 + 删 role/路由 + 停备份 + 留审计
```

### 5.2 平台「统一管理」具体管这 7 件事

| 管什么         | 怎么管                                                                | 归属                     |
| -------------- | --------------------------------------------------------------------- | ------------------------ |
| 建库 / 建 role | 部署前自动，专用 role 仅能访问自己库                                  | pgsupply                 |
| 连接串供给     | 写入 `appdeploy_env` 的 `DATABASE_URL` 行，部署时 `-e` 注入           | pgsupply → appdeploy     |
| 备份恢复       | 定时 `pg_dump app_<id>` → `data/backups/<project>/<app>/`，可单库恢复 | pgsupply                 |
| schema 迁移    | 平台触发「对 app 库跑应用仓自带 migrations」，记录 `schema_version`   | pgsupply                 |
| 监控           | 采集连接数 / 库大小 / 慢查询，聚合到应用健康度                        | pgsupply + ops           |
| 配额           | 库大小 / 连接数 / 表数限额，按 `project_quota`                        | pgsupply + project_quota |
| 连接管理       | 每项目独立 PG 实例，组内应用少、直连即可（无 pgbouncer，避开兼容坑）  | pgsupply                 |

### 5.3 数据模型（新增表）

#### `appdeploy_database` —— 应用库供给记录（库元数据 + 生命周期）

```sql
CREATE TABLE appdeploy_database (
    id               TEXT PRIMARY KEY,
    app_id           TEXT NOT NULL REFERENCES appdeploy_application(id) ON DELETE CASCADE,
    project_space_id TEXT NOT NULL,
    db_name          TEXT NOT NULL,                 -- app_<shortid>，PG database 名
    db_role          TEXT NOT NULL,                 -- 专用 PG role 名（仅本库权限）
    pg_instance_id   TEXT NOT NULL,                 -- 所属 PG 实例（pg_instance.id）
    db_host          TEXT NOT NULL,                 -- 实际 host（来自 pg_instance，冗余便于直连/排障）
    db_port          INT  NOT NULL DEFAULT 5432,
    status           TEXT NOT NULL,                 -- provisioning/ready/failed/deleted
    last_error       TEXT,
    backup_enabled   BOOLEAN NOT NULL DEFAULT TRUE,
    last_backup_at   TIMESTAMP,
    schema_version   TEXT,                          -- 应用库已迁移到的版本号
    created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(db_name),
    UNIQUE(app_id)                                  -- 每应用一个库（database-per-app）
);
CREATE INDEX idx_appdb_ps ON appdeploy_database(project_space_id);

-- pg_instance：PG 实例注册表（每项目一个独立 PG 实例；平台纳管，可独立部署到多机）
CREATE TABLE pg_instance (
    id               TEXT PRIMARY KEY,              -- pg-<project> …
    project_space_id TEXT NOT NULL REFERENCES project_space(id) ON DELETE CASCADE, -- 归属项目（默认 1:1，允许手动拆）
    host             TEXT NOT NULL,                 -- PG 主机（docker 服务名或 IP，可跨机）
    port             INT  NOT NULL DEFAULT 5432,    -- PG 端口（应用直连，无 pgbouncer）
    admin_url_ref    TEXT NOT NULL,                 -- 该实例管理账号引用（加密存储的 key）
    deploy_mode      TEXT NOT NULL DEFAULT 'managed', -- managed(docker起PG容器) / external(纳管远程已有PG)
    status           TEXT NOT NULL,                 -- active / draining / maintenance
    created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_pginst_ps ON pg_instance(project_space_id);
CREATE INDEX idx_pginst_status ON pg_instance(status);
```

> **密码不入此表**：连接串以 `DATABASE_URL` 形式存于 `appdeploy_env`（`is_secret=TRUE`，接口 mask 显示，与现有 secret 处理一致）。本表只存库的「元数据 + 生命周期 + 备份/迁移版本」。

### 5.4 `pgsupply` 模块设计（新增 `internal/pgsupply/`）

```
internal/pgsupply/
├── instance.go    // pg_instance 注册表 + 按项目 GetOrCreateInstance（managed:docker起PG容器 / external:纳管远程）
├── supply.go      // Provisioner: 取项目实例 → 建库 + 建 role + 授权 + 生成直连连接串
├── backup.go      // 定时 pg_dump / 恢复（按实例）
├── migrate.go     // 对 app 库触发应用自带 migrations（按 app 库连接）
├── store.go       // appdeploy_database / pg_instance 的 CRUD
├── model.go
└── supply_test.go
```

**`Provisioner` 核心流程**（持平台管理账号连接）：

1. 校验项目配额（`project_quota.max_databases` 未满）
2. **取/建项目 PG 实例**：`GetOrCreateInstance(project_space_id)` —— 该项目已有 active 实例则复用；没有则 ProvisionInstance（managed：docker 起一个 PG 容器 + 分配端口 + 写 pg_instance；external：纳管远程已有 PG）
3. 连该实例管理账号：`CREATE DATABASE app_<shortid>`
4. `CREATE ROLE app_<shortid>_role WITH LOGIN PASSWORD '<rand>'`（组内应用少，无需严格 CONNECTION LIMIT）
5. `GRANT ALL ON DATABASE app_<shortid> TO app_<shortid>_role`（仅本库）
6. 生成 `DATABASE_URL` —— **直连项目 PG 实例**：`postgres://app_<shortid>_role:<pwd>@<host>:<port>/app_<shortid>?sslmode=disable`（无 pgbouncer，避开 transaction-pool / prepared-statement 兼容坑）
7. 写 `appdeploy_database`（含 `pg_instance_id`，status=ready）+ `appdeploy_env` 的 `DATABASE_URL` 行（is_secret=TRUE）

**关键约束**：

- 每个 PG 实例配独立「平台管理账号」（`pg_instance.admin_url_ref`），仅在供给/备份/迁移时使用，**不**作为应用运行时连接。
- **每项目一个独立 PG 实例**，应用直连（无 pgbouncer），避开 transaction-pool / prepared-statement 兼容坑。
- **新项目首次建应用 = 自动 ProvisionInstance**（managed：docker 起一个 PG 容器）；也支持 external 模式纳管远程已有 PG。
- 同项目应用多了要拆：`pg_instance` 允许一个 project_space 多个实例（手动加 + 迁移部分应用 `pg_instance_id`），默认 1:1。
- 热点应用可手动指定独立 `pg_instance_id`，避免「吵闹邻居」。

### 5.5 迁移机制（平台库 vs 应用库，明确区分）

| 维度         | 平台库（`anp`）                          | 应用库（`app_<id>`）                   |
| ------------ | ---------------------------------------- | -------------------------------------- |
| 迁移文件     | `migrations/pg/*.sql`（embed，平台维护） | 应用仓自带（prisma/alembic/goose 等）  |
| 触发时机     | backend 启动 + `make migrate-up`         | appdeploy 部署成功后，由 pgsupply 触发 |
| 版本记录     | `anp.schema_migrations`                  | `appdeploy_database.schema_version`    |
| 谁负责表结构 | 平台                                     | **应用**（平台不碰业务表）             |

> 应用库迁移策略：优先让应用**启动时自迁移**（多数框架默认行为，`DATABASE_URL` 一给就行）；对不自迁移的应用，平台提供「按 app 库跑指定 SQL 目录」的托管能力（阶段 3 实现）。阶段 1 不强制。

### 5.6 备份恢复

- 定时任务：每日 `pg_dump --format=custom app_<id>` → `data/backups/<project_space>/<app>/YYYYMMDD.dump`
- 保留策略：近 7 日每日 + 近 4 周每周（可配）
- 恢复：`pg_restore` 到新库或覆盖，平台 UI 提供单应用恢复入口
- 归档：删除应用时 `backup_enabled=FALSE` 但保留最后一次备份 N 天

## 6. API 统一入口（网关）

### 6.1 架构：nginx（入口）+ appgw（应用网关）

```
外部请求 /apps/<appcode>/...
   │
   ▼
nginx(8088) ── location /apps/ ──▶ appgw(Go, ReverseProxy)
                                    │
                                    ├─ 读 appdeploy_route 表 → 解析 upstream(容器 host:port)
                                    ├─ 鉴权：验平台 JWT（用户）或 capability APIKey（M2M）
                                    ├─ 注入 X-User / X-Project-Space-Id / X-Trace-Id
                                    ├─ 计量：记 appgw_access_log
                                    └─ ReverseProxy → 应用容器(http://<host>:<port>)
```

**为什么 nginx + appgw 两段，而不是 nginx 直接动态路由**：

- nginx 难以实时查 PG 路由表（需 lua 或 reload，复杂且 reload 有抖动）
- appgw 是轻量 Go 服务，复用 backend 的 PG 连接 / 鉴权 / ProjectSpaceInjector，ReverseProxy 天然适合
- nginx 仍负责入口 TLS、静态前缀分流（`/api/` `/apps/` `/agent/`），职责清晰

**部署独立性**：appgw 只依赖 PG 路由表（可内存缓存 + 定时刷新），backend 故障时已部署应用仍可对外服务（应用可用性不耦合平台 backend）。

> **演进**：阶段 2 初期可先把 appgw 作为 backend 的一个路由组（`/apps/`）快速验证，验证通过后拆为独立服务 `cmd/appgw/main.go`。

### 6.2 路由表（新增表）

#### `appdeploy_route` —— 应用对外路由（appgw 消费）

```sql
CREATE TABLE appdeploy_route (
    id               TEXT PRIMARY KEY,
    app_id           TEXT NOT NULL REFERENCES appdeploy_application(id) ON DELETE CASCADE,
    project_space_id TEXT NOT NULL,
    app_code         TEXT NOT NULL,                 -- URL 路径段：/apps/<app_code>/
    env              TEXT NOT NULL,                 -- test / prod
    upstream_host    TEXT NOT NULL,                 -- 容器可达 host（compose 网络内为宿主或网关可达地址）
    upstream_port    INT  NOT NULL,                 -- 容器端口（appdeploy 分配的 HostPort）
    status           TEXT NOT NULL,                 -- active / inactive
    auth_required    BOOLEAN NOT NULL DEFAULT TRUE, -- 是否强制平台身份
    created_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(app_code, env)
);
CREATE INDEX idx_route_code ON appdeploy_route(app_code, env) WHERE status='active';
```

### 6.3 URL 形态与路由机制

- **对外统一**：`http://<平台入口>:8088/apps/<app_code>/` → appgw → 应用容器
- **环境区分**：`/apps/<app_code>/`（prod）；test 环境走 `/apps/<app_code>~test/` 或独立前缀（阶段 2 定）
- **内网直连（保留）**：`http://10.10.0.28:9xxx` 仅供调试 / 平台内部调用，不对公网暴露
- **部署即登记**：`appdeploy.Deploy()` 成功后，写 / 更新 `appdeploy_route`（status=active），appgw 下次刷新即生效（≤10s）

### 6.4 鉴权与身份打通

| 场景              | 凭证                                | 流程                                                                      |
| ----------------- | ----------------------------------- | ------------------------------------------------------------------------- |
| 用户访问应用      | 平台 JWT（Authorization: Bearer）   | appgw 验签 → 注入 `X-User` / `X-Project-Space-Id` → 转发；应用可选校验    |
| 应用调平台 AI     | capability APIKey（已有）           | 应用持 APIKey 调 `/api/v1/capability/invoke`，已有 Gateway 鉴权 + 计量    |
| 应用间互调（M2M） | capability APIKey（新增 m2m scope） | 调用方应用持 APIKey 经 appgw 访问被调应用，appgw 校验 AllowedSkills/Scope |

> 身份注入复用现有 `ProjectSpaceInjector` 中间件思路（已从 header 读 `X-Project-Space-Id`）。appgw 把用户身份透传给应用，应用侧是否强制校验由应用决定（`appdeploy_route.auth_required` 控制 appgw 是否拦截未认证请求）。

### 6.5 计量与可观测

- **访问日志**：新增 `appgw_access_log`（app_code / caller / latency / status / trace_id）—— 阶段 3
- **指标聚合**：每应用 QPS / 延迟 / 错误率，并入 ops 健康度
- **trace 串联**：appgw 生成 / 透传 `X-Trace-Id`（已有 `Trace()` 中间件）

## 11. 风险与对策

| 风险                                             | 对策                                                                                                             |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 平台管理账号（`PG_ADMIN_URL`）权限过大，泄露危险 | 仅在 pgsupply 内部使用，不进应用容器；密钥走 `.env.prod` + `appdeploy_env is_secret` mask；审计所有建库/删库操作 |
| 应用库数量增多，PG 连接数压力                    | **按项目拆实例**（每项目独立 PG，组内应用少连接可控）；应用侧连接池限流；监控每实例连接数                        |
| appgw 成为应用流量关键路径                       | appgw 内存缓存路由表 + 定时刷新，PG 短暂不可用时仍可用；独立服务隔离 backend 故障                                |
| 应用自带 DB（非 PG）绕过供给                     | 平台默认只注入 `DATABASE_URL`（PG）；应用若强行用 sqlite 等则不纳入备份/管控（属应用自担风险，文档明确）         |
| 单项目 PG 实例故障影响该项目应用                 | 按项目隔离（故障只影响一个项目）；实例配流复制主从；阶段 1 先靠 pg_dump 兜底；实例可 drain 下线                  |
| 端口段（9100-9300）耗尽                          | 配额 `max_apps` 限制；长期可改 appgw 内部转发，不再每应用占宿主端口                                              |

### 扩展性演进路径（多机 / K8s，按需推进，YAGNI）

| 触发条件                               | 方案              | 动作                                                      |
| -------------------------------------- | ----------------- | --------------------------------------------------------- |
| 某项目应用多 / 负载重                  | **项目内拆实例**  | `pg_instance` 为该项目加第二个实例，迁移部分应用（手动）  |
| 要把项目 PG 分布到第二台机器           | **跨机部署实例**  | ProvisionInstance 远程机起 PG 容器 / external 纳管远程 PG |
| 应用容器 CPU / 内存 / 端口吃紧，要跨机 | **docker swarm**  | docker 原生轻量编排，几乎零学习成本，跨机调度应用容器     |
| PG 单点要高可用                        | **PG 流复制主从** | repmgr + VIP，裸机 / 容器跑，不用 operator                |
| 真正需弹性伸缩 / 多集群 / 多团队自服务 | **K8s**（远期）   | 此时再上，operator 管 PG                                  |

> 原则：**现在不上 K8s、不用 pgbouncer**。隔离靠每项目独立 PG 实例；扩展靠项目内拆实例 / 跨机部署 + docker swarm 过渡。K8s 的运维税只在「弹性伸缩 / 多团队」场景才值回票价。

## 12. 不在本期范围（YAGNI）

- 应用库**跨实例在线迁移**（建库时选实例已支持；运行中把库搬到另一实例的在线迁移不做）
- 应用库自动 schema 审计 / 漂移检测
- 应用间事件总线 / 消息队列（仅 M2M 同步调用）
- **K8s 编排 / 异地容灾 / 多集群**（本期 docker swarm 级别够用）
- PG 分库（citus）/ 写扩展
- 应用市场 / 公开应用商店语义
- 非 PG 数据库（mongo/redis 等）的统一供给（本期只 PG）

## 13. 验收标准（整体）

1. **注册即纳管**：在平台创建任意应用，自动获得独立 `app_<id>` 库 + 注入 `DATABASE_URL`，无需人工干预
2. **统一入口**：所有应用对外走 `/apps/<code>/`，经平台鉴权，裸端口仅内网可达
3. **集中备份**：任一应用库可由平台 pg_dump 备份并恢复
4. **三层清晰**：平台级（建库发路由）/ 项目级（配额成员）/ 应用级（业务表）边界无歧义
5. **可观测**：每应用的库大小、连接数、API 调用量、健康度在平台可见
6. **零回归**：现有应用部署流程（需求 → 派发 → 构建 → 发布）不受破坏，`DATABASE_URL` 是增量注入
