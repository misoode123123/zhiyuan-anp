## 0. 决策背景（为什么改道）

原 P2 设计是「opencode 部署前**备料**」：AI 只校准 `.anp/deploy.yaml` 的 needs 声明，
固定引擎照声明执行。用户评审后**改道**：

> 「确定用 AI 直接部署，做好对 AI 的要求跟限制。」

即：执行层也交给 opencode，但平台保留硬约束与验证权。原备料方向的核心资产
（needs 声明、简报、`.anp/` 目录约定）全部保留并升级为 AI 执行的输入契约。

**分工不变的部分**：RBAC / 变更闸门 / AC7 delivered 前置 / 测试门禁全在 AI 之前的
同步门禁段（平台先鉴权，AI 永远碰不到审批链）。

## 1. 总体架构

```
点击部署(test) → [同步门禁段: RBAC/变更闸门/AC7 — 不变]
              → markPreparing → go aiDeploy:
                  1. 平台组装部署简报(.anp/deploy-brief.md)
                  2. opencode run --auto 在受限 shell 中执行部署
                  3. 平台验证(不信 AI 自报): 容器实态回读
                  4. 验证过 → RecordActuals(从容器实态) → running
              状态机: preparing → (verifying) → running / failed(+回滚)
```

- **引擎开关**：`system_config.deploy_engine`，`fixed`（默认）/ `ai`。
  - `ai` 仅对 **env=test** 生效；**prod 恒走 fixed**（放开 prod 是后续配置项，跑稳后）。
  - `fixed` = 现链 `buildAndDeploy` 一字不动。
- Promote（上线 prod）不走 AI 部署。
- 状态机新增 `preparing`（instance.status），前端复用 building 的展示模式
  （黄条 + 文案「AI 部署中…」）。

## 2. 部署简报（平台 → AI 的输入契约）

平台写 `<repoDir>/.anp/deploy-brief.md`，opencode prompt 引用它。

```markdown
# 部署简报：{app.name} → {env} v{version}

## 硬性规则（违反=部署判失败）

- 容器名必须: appdeploy-{slug}-{env}-v{version}
- 宿主端口必须用: {preAllocatedPort}（已预留，不许自选）
- 只能操作 name 前缀 appdeploy-{slug}- 的容器（先清理旧版本再起新的）
- 密钥 {envKeys} 已注入你的环境变量，禁止把值写进任何文件/日志

## 应用上下文

- 仓库: {repoDir}
- 声明: 监听端口 {needs.ports} / 启动命令 {needs.command} / 挂载 {needs.mounts} / env_keys {needs.env_keys}
- 上次成功部署参数(actual，供参考): {actual}

## 你的任务

分析代码与简报 → 构建镜像 → 清理旧容器 → 启动新容器 → 自检（容器 Up + 探活）
→ 写 .anp/deploy-result.yaml（平台将校验）
```

`.anp/deploy-result.yaml`（AI 的结构化回报）：

```yaml
container: appdeploy-x-test-v11
image: appdeploy/x-test:v11
listen_port: 8080
command: "python -m http.server 8080"
mounts:
  - src: config.yaml
    dst: /app/config.yaml
notes: "" # 超出 needs 模型的处理说明（给平台维护者）
```

要点：

- **宿主端口由平台预分配**（复用 `AllocFreePort`，AI 不自选）——端口治理不交 AI。
- 简报里的 needs/actual 全部来自 `.anp/deploy.yaml`（P1 已有），无新表。
- 版本号 `v{version}` 由平台自增（沿用 ins.Version++），镜像 tag 命名规则写进简报。

## 3. 受限执行环境

复用 `dev/coding.go:148 opencodeRun` 模式（opencode run --auto，30min→**15min** 部署超时），
加**命令白名单 shim**：

- AI 进程的 `PATH` 只含 `/usr/local/bin/anp-docker-shim/`（目录内仅一个 `docker` 包装脚本，
  真实 docker 二进制由 shim 以绝对路径转发；其余命令在 PATH 中找不到=天然拒绝）：
  - 放行子命令：`docker build|run|inspect|logs|ps`
  - `docker stop|rm` 限容器名前缀 `appdeploy-{slug}-`，碰其他容器一律拒绝并记录
    （防误停 deploy_backend 等平台容器）
  - `docker run` 的端口/命名违规不在 shim 拦（无法静态判定），由 §4 验证判失败
- shim 拒绝记录追加进 build_log（可见 AI 试图执行什么）。
- 密钥经环境变量注入；shim 对 stdout/stderr 做**已知 key 值替换脱敏**后落 build_log。
- shim 本身是平台维护的 shell 脚本（部署进 backend 镜像），代码评审把关。

## 4. 平台验证（不信 AI 自报）

AI 退出后依次验证，任一不过 → `failed` + **自动回滚**。回滚由平台执行（非 AI）：旧容器
已被 AI 按简报清理、无法「重启」，故回滚=平台以固定引擎按 deploy.yaml actual（P1
resolved-priority 重放）重跑上一版本镜像；首版部署无上一版则仅清理残留容器后置 failed：

1. `.anp/deploy-result.yaml` 存在且 schema 合法
2. `docker inspect {container}` 存在且 `State.Running`
3. 容器名匹配 `appdeploy-{slug}-{env}-v{version}`；宿主端口 == 预分配端口
4. 探活：`/healthz` 或 TCP listen（复用现有 InspectHealth）
5. 镜像引用 == `deploy-result.image`

全过 → `RecordActuals` **从容器实态回读**（InspectImage + HostPort），非 AI 报告 →
`running`。

build_log = 简报全文 + AI 每条命令及输出（脱敏后）+ 验证五步结果。审计、变更闸门、
审批链照旧。

## 5. 失败降级

- AI 部署失败（超时 / 验证不过 / shim 致命拒绝）→ 状态 `failed` + build_log 全记录。
- 前端一键「**用固定引擎重试**」按钮（failed 状态时显示）→ 走现链 `buildAndDeploy`。
- **不自动静默降级**——失败必须可见，人工选择重试方式（用户「别静默」原则）。
- 区分：**回滚**（自动，恢复上一版服务，保可用性）≠ **降级**（人工，固定引擎重跑本次失败
  部署）——自动的只有前者。

## 6. 数据模型变更

| 变更                             | 类型     | 说明                                |
| -------------------------------- | -------- | ----------------------------------- |
| `system_config.deploy_engine`    | 配置行   | fixed(默认)/ai；ai 仅 test 生效     |
| instance.status 新值 `preparing` | 枚举扩展 | 无迁移（status 是文本列）           |
| `.anp/deploy-brief.md`           | 临时文件 | 部署时写，验证后删                  |
| `.anp/deploy-result.yaml`        | 临时文件 | AI 回报，验证后并入 actual 记录后删 |
| `deploy_node`/表结构             | 不变     | 零迁移                              |

## 7. 测试策略

- **纯单测**（无 docker/PG）：简报组装（密钥不落明文）；deploy-result 解析与 schema
  校验；验证规则（假 inspect 输出驱动）；shim 白名单判定（纯函数化子命令解析）。
- **集成**（PG anp_test + fake opencode）：`aiDeploy` 全链——fake `opencode` 可执行
  脚本（写出合法/非法 deploy-result 两态）驱动，断言状态迁移、回滚、build_log 脱敏。
- **.28 e2e**：`deploy_engine=ai` + 真实应用 test 部署；验证简报落盘、容器名/端口合规、
  故意断网一个场景验证失败回滚与「固定引擎重试」按钮。

## 8. 关键决策记录

| 决策              | 选择                             | 理由                                                   |
| ----------------- | -------------------------------- | ------------------------------------------------------ |
| 执行层归属        | AI 直接执行（用户改道决策）      | 灵活性最大化；平台以约束+验证兜底                      |
| prod 是否 AI 部署 | 否，恒 fixed（先 test）          | prod 是对已验证 test 的提升；跑稳一周再放开            |
| 端口分配权        | 平台预分配                       | 端口治理（段位/冲突/DriftReconciler 识别）不交概率系统 |
| 验证依据          | 容器实态回读，非 AI 自报         | AI 结论不可信原则；实态是唯一真相                      |
| 失败降级          | 显式 failed + 人工选固定引擎重试 | 别静默；失败可见                                       |
| 固定引擎去留      | 保留（默认引擎）                 | 应急通道 + prod 主力；不删                             |
| needs 声明去留    | 保留，升级为简报输入             | AI 上下文的一部分；actual 重放基准不变                 |

## 9. 不做 / follow-up

- ❌ AI 部署 prod（跑稳后经配置放开）
- ❌ shim 白名单外的命令按需放行（出现真实需求再评估）
- ❌ AI 自选宿主端口
- 📌 follow-up：deploy-result.notes 累积的「超出 needs 模型」案例反哺 needs 字段扩展
- 📌 follow-up：AI 部署成功率的运营统计（成功率/平均耗时/失败 top 原因）
