# ANP 部署消费 adapt 产物 — 教训与优化总结

> 日期：2026-08-04 ｜ 关联 spec：[2026-08-04-部署消费adapt-config挂载与mw实例注册-design.md](2026-08-04-部署消费adapt-config挂载与mw实例注册-design.md)
> 触发：导入真实复杂项目 `yxt_eino_v2`（Go 客服机器人,多 cmd + Redis/Milvus/PG 依赖 + config.yaml）端到端测试 ANP「导入→adapt→部署」全流程。

## 1. 核心结论

**ANP 的 opencode adapt（改造代码）已达生产级,但部署侧没把 adapt 的假设消费到位**——这是本次实测的核心教训。adapt 写了 `env.go` 读 REDIS_ADDR/MILVUS_ADDR、Dockerfile 假设 config secret 挂载、声明 deps,但部署侧没挂 config、没注入 env、连不到依赖网络,导致应用 build 过却跑不起来。

## 2. 发现的缺口（实测暴露）

| #   | 缺口               | 现状                                                                                                                                                                 | 手动补丁                                                |
| --- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| ①   | config.yaml 没挂载 | adapt 假设 ANP 把 config.yaml 作 secret 挂到 CONFIG_PATH;`deployer.Deploy` 无 volume 机制                                                                            | 改 Dockerfile COPY config.yaml(打进镜像,违 secret 语义) |
| ②   | mw env 没注入      | adapt env.go 读 REDIS_ADDR 等,deps 声明 redis/milvus;但 bind_existing 依赖 ServiceInstance 注册表,docker-compose 起的 yxt-redis 等没注册 → Reconcile 找不到 → 不注入 | UpsertEnv 8 个 env 指向宿主 IP+映射端口                 |
| ③   | 容器网络隔离       | ANP 应用 bridge 网络,DNS 8.8.8.8 解析不了依赖网络(yxt-infra_default)的服务名                                                                                         | env 改用宿主 IP+映射端口(10.10.0.28:6381 等)            |
| ④   | deps 不完整        | adapt deps.yaml 只声明 redis/milvus,漏 PG(env.go 覆盖了但没声明给 ANP 供给)                                                                                          | 手动 UpsertEnv PG_HOST 等                               |

## 3. 本次优化（已做）

- **① config 挂载** ✅ 已合 main + 部署 .28
  - `Deploy` 加 configPath volume(`-v <path>:/app/config.yaml:ro`)
  - `buildAndDeploy` 检测 `<RepoDir>/config.yaml` + 注入 `CONFIG_PATH` env
  - 兑现 adapt secret 挂载假设,密钥不进镜像层
- **② mw 实例注册** ✅ store + API 已 commit(main 本地)
  - `Store.RegisterBindExisting/ListBindExisting`(幂等,项目级优先)
  - `mw-instances` API:`POST/GET/DELETE /project-spaces/:id/mw-instances`(admin 鉴权)
  - Reconcile 现有逻辑:注册后 LookupBindExisting 命中即自动注入 env
- **③④ 待续**:网络对接 / deps 完整性(PG 多 env)

## 4. 教训

1. **adapt 生产级,部署消费是短板**:opencode 读码系统性改造(env-over-config 架构 + Dockerfile 双端口/HEALTHCHECK + deps 声明,681 行),非模板套用;但部署侧必须兑现 adapt 的假设(secret 挂载 / env 注入 / 网络),否则「build 过、跑不起」。
2. **实测出真知**:单元测试覆盖不到部署消费缺口(都 mock 了 docker/env),只有真实复杂项目端到端才暴露。dogfooding 应常态化。
3. **bind_existing 的发现盲区**:依赖「预注册的 ServiceInstance」,但部署机上 docker-compose/手动起的服务不会被自动发现 → 需运行时注册 API(本次②)或自动探测(后续)。
4. **网络是隐性坑**:bridge 容器与依赖网络隔离,DNS 解析失败比连接拒绝更迷惑;host 网络 / 宿主IP / 加入依赖网络 三选一,要明确策略。
