# PRD/设计：主线闭环收敛（需求→研发→测试→审批→发布 真正合上）

| 版本 | 日期       | 作者     | 状态   |
| ---- | ---------- | -------- | ------ |
| v1.0 | 2026-07-26 | ANP 团队 | 待评审 |

> 取证见本轮「主线闭环样本模拟」调查。本文是排查「实际操作中不能闭环测试」后，对**设计层根因**的修复方案。审核通过后再开发。

## 1. 背景与目标

README 声称「主线闭环已端到端打通」：`需求(specified)→派发编码(developing)→测试→G3审批(approved)→发布(released)→需求 delivered`。但用一个样本真驱动后发现**闭环从未合上**：

- `.28/anp_dev` 真实库里 `requirement` **零 delivered**；`chg_demo1` 已 `released`，但其来源 `req_demo` 仍停在 `developing`，且 `release_record` 表为空。
- `code_task` 表为空——**dispatch-code 主线在任何环境都从未跑到完成**（demo 数据是直接 seed 的）。
- 实测：用 appdeploy 路径产的变更走发布中心，接口返回 201 + note「需求已交付」，但需求 status 实际没变。

**目标**：让「发布」真正闭环——无论变更来自 dispatch-code 还是 appdeploy 交互编码，发布后来源需求都正确标记 `delivered`，且发布动作不可绕过审批、不可谎报成功。

## 2. 现状（已取证）

### 2.1 变更 `source_id` 语义二义（根因）

`change.source_id` 被重载，两条产变更路径写不同东西：

| 产变更路径                                 | source_id 写入            | 位置                                                               |
| ------------------------------------------ | ------------------------- | ------------------------------------------------------------------ |
| dispatch-code（需求驱动编码）              | `requirement.id`（reqID） | `dev/coding.go:124`                                                |
| appdeploy `RegisterChange`（交互编码登记） | `application.id`（appID） | `appdeploy/handler.go:281`（注释 `:206` 明写「source_id=应用ID」） |
| appdeploy `Submit`（核对门禁自动登记）     | `application.id`（appID） | `appdeploy/handler.go:480`                                         |

而 `release.Create` 三处都把 `chg.SourceID` 当 `requirement_id` 用：

- 门禁 `PassedCountByRequirement(chg.SourceID)`（`release/handler.go:88-93`）
- 回写 `UpdateStatus(chg.SourceID, "delivered")`（`release/handler.go:110-114`）
- 部署 `reqRepo.Get(chg.SourceID).ApplicationID`（`release/handler.go:118-124`）

→ **appdeploy 路径的变更（source_id=appID）走发布中心时三步全错位**：门禁恒 0、回写匹配 0 行、部署取不到需求。

### 2.2 发布中心不校验审批（可绕过 G3）

`release.Create`（`release/handler.go:75-130`）全程**未校验 `chg.Status=="approved"`**——只查测试门禁（且默认关）。一个 `pending`（未审批）变更可直接发布。对比 `/merge` 有 `HasApproved` 前置（`appdeploy/handler.go:523`），发布中心反而更松。

### 2.3 回写「谎报成功」（最误导）

- `release/handler.go:112`：`_ = h.reqRepo.UpdateStatus(...)` —— **返回值被丢弃**，不知道是否真有行被更新。
- `release/handler.go:128-130`：响应 `note` 依据 `deployed == ""` 判定，与回写是否成功**无关**。
- 实测：变更 `chg_1da11faa`（source_id=`app_demo`）发布 → 返回 201 + note「需求已交付（来源需求未归属应用…）」，但 `req_9395627364014e6994a7` status 仍是 `specified`。**接口说成功，状态没变。**

### 2.4 三条「交付/上线」写入路径不收敛

| 路径                                        | 写 delivered?          | 建 release_record?      | 位置                           |
| ------------------------------------------- | ---------------------- | ----------------------- | ------------------------------ |
| 发布中心 `release.Create`                   | ✅（按 source_id）     | ✅                      | `release/handler.go:110-114`   |
| `/merge`（合并 dev 分支）                   | ✅（按 body `req_id`） | ❌                      | `appdeploy/handler.go:543`     |
| `/promote`、`/deploy env=prod`（上线 prod） | ❌                     | ❌（只 `MarkReleased`） | `appdeploy/handler.go:950,998` |

demo 数据走的是第 3 条 → 既没回写 delivered，也没建 release_record → 这就是 `chg_demo1=released` 但 `req_demo=developing`、`release_record` 为空的由来。

### 2.5 schema 债（加重排查难度）

`change_request.application_id`（`migrations/pg/000001_init.up.sql:93`）、`release_record.application_id`（`:127`）两列**存在但从不写入**，恒 NULL。应用归属靠查询时双路径 JOIN 临时推导（`change/store.go:32-40`）。

## 3. 设计

### 3.1 统一 `source_id` 语义为 requirement_id（核心）

让两条产变更路径都产出 `source_id = reqID`，发布中心即可 uniformly 正确：

- **appdeploy `RegisterChange`/`Submit`**：当请求带 `req_id` 时，`SourceID = reqID`（不再写 `aid`），并把应用归属写入 `change.application_id = aid`（激活目前恒 NULL 的列）。
  - `RegisterChange` 已收 `req_id`（`appdeploy/handler.go:234`），目前只塞进 output 文本（`:256-257`），改为写 `SourceID`。
  - `Submit` 已收 `req_id`（`:424`，必填），同样改 `SourceID = reqID` + `application_id = aid`。
- **dispatch-code** 不变（已是 reqID）。
- **查询侧**：`change/store.go` 的双路径 JOIN（`appSourceCond`）改为统一走 `change.application_id`，过渡期可保留 `OR source_id=appID` 兼容旧数据，迁移完成后删兼容分支。

> 备选方案 B（加独立 `requirement_id` 列）：语义更干净但要 schema 迁移 + 改全部 JOIN，且不解决「source_id 仍二义」。**推荐方案 A**：改动最小，顺带激活 `application_id` 列，与现有「release 拿 source_id 当 reqID」的方向一致。

### 3.2 发布中心加 G3 审批前置

`release.Create` 取 `chg` 后（`:84-86` 之后）加：

```go
if chg == nil || chg.Status != "approved" {
    httpx.Err(c, 409, 40902, "发布前置未满足：变更需先经 🚪G3 审批（approved）。")
    return
}
```

与 `/merge` 的 `HasApproved` 闸门对齐。发布中心 = G5（审批后），不应放行 pending。

### 3.3 回写不得谎报（失败要可见）

- `Repository.UpdateStatus`（`requirement/repository.go:80`）改为返回 rows-affected：

  ```go
  res, err := r.db.ExecContext(...)
  n, _ := res.RowsAffected()
  return n, err
  ```

- `release.Create` 据回写真实结果生成 `note`：

  ```go
  rowsDelivered := 0
  if h.reqRepo != nil { rowsDelivered, _ = h.reqRepo.UpdateStatus(ctx, chg.SourceID, "delivered") }
  ```
  - `rowsDelivered == 0` → note 如实「未关联到需求（source_id 未解析到 requirement），需求状态未变更」，**不得**写「需求已交付」，并考虑返回 `422`/告警码让前端感知。
  - `rowsDelivered > 0` → 才写「需求已交付」。

### 3.4 三路径状态语义澄清（文档化 + 轻校验）

明确两个概念不同：

- `requirement.status = delivered`：功能已发布（**唯一写入点 = `release.Create`**）。
- `change.status = released`：已上线 prod（`/promote`、`/deploy env=prod` 的 `MarkReleased`）。

收敛规则：

- **发布中心**是交付闭环的唯一动作（建 release_record + delivered + 触发 test 部署）。
- **`/promote`（上线 prod）** 前置要求「来源变更已 approved 且来源需求已 delivered」；未交付时提示「请先到发布中心发布」。避免 demo 数据那种「promote 了但没交付」的断链。
- `/merge` 的 delivered 写入保留（本地合并场景），但文档标注为发布中心的等价替代，不作为主路径。

### 3.5 dogfood 前置（验收必做）

`code_task` 表至今为空——主线从未端到端跑通。本次实现须在 `.28` 上真驱动一次：

```
dispatch-code → code_task completed(+change_id) → generate-tests → run-tests/manual-verdict → approve → release → requirement.status=delivered
```

## 4. 验收标准

| 编号 | 验收点                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------- |
| AC1  | `RegisterChange`/`Submit` 带 `req_id` → 变更 `source_id = reqID`（非 appID），`application_id = aid`                          |
| AC2  | `release.Create` 对 `pending` 变更 → 409；对 `approved` 变更 → 200                                                            |
| AC3  | appdeploy 路径变更经 approve + release 后，来源需求 `status = delivered`（不再静默失败）                                      |
| AC4  | `source_id` 未解析到需求时，响应 note 如实告警，**不含**「需求已交付」；`UpdateStatus` 返回 rows-affected                     |
| AC5  | `.28` 端到端：dispatch-code 跑通 → `code_task` 表首次出现 `completed` 记录且带 `change_id` → 全链路至 `requirement=delivered` |
| AC6  | 门禁开时，appdeploy 路径变更（现 source_id=reqID）能靠 manual-verdict 满足 `passed≥1` 放行（不再恒拦）                        |
| AC7  | `/promote` 对未 delivered 的来源需求 → 拒绝并提示先发布                                                                       |

## 5. 不在本次范围

- **Windows 本地 dispatch 失败（`exit status 0xc0000142`）**：环境问题（子进程 DLL 初始化），闭环验证统一在 `.28`（Linux）。
- **PG 编码**：已确认 `.28/anp_dev` 为 UTF8 + en_US.utf8，**无编码 bug**（早期怀疑的「中文乱码」经 hex 验证为 Windows 测试控制台显示问题，数据本身正确）。
- **codex 工作台 stub、24h 认领超时 cron、并发任务队列化**：均已知遗留，另立。
- **编码完成 race（断点A）**：`MarkCompleted` 先于建变更致 `change_id` 短暂 null。建议顺带调整 `dev/coding.go:120-129` 顺序（先建变更再 MarkCompleted），但单列任务。

## 6. 影响面

- 后端：`internal/appdeploy/handler.go`（RegisterChange/Submit 的 SourceID）、`internal/release/handler.go`（审批前置 + 回写真实结果）、`internal/requirement/repository.go`（UpdateStatus 返回值）、`internal/change/store.go`（JOIN 统一）。
- 数据：旧 appdeploy 变更（source_id=appID）需一次性回填——按 `requirement.application_id`/output 文本里的 req_id 反查补 `source_id`，或标记为legacy不参与闭环。
- 前端：若发布中心与「🚀上线」按钮的链路有重叠，需对齐到 3.4 的收敛规则（具体待前端确认）。
