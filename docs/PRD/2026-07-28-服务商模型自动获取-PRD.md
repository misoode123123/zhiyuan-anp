# PRD：配置服务商/模型时自动对接服务商获取模型信息

| 版本 | 日期       | 作者     | 状态                |
| ---- | ---------- | -------- | ------------------- |
| v0.1 | 2026-07-28 | ANP 团队 | **先登记·后期开发** |

> 本需求**仅登记，暂不开发**。后期排期实现。

## 1. 背景与目标

**现状痛点**：在「算力资源」配置模型服务商（provider）和模型（model）时，模型信息（服务 ID、context 窗口、最大输出、是否 reasoning 等）**完全手工填写**。手工填易错，已多次踩坑：

- 2026-07-28：腾讯混元 MaaS 的 API Key 填错一个字符（`j9`→`j7`），服务一直 401「key 不存在」。
- 2026-07-28：模型服务 ID 填成 `glm5.2`（无横杠），腾讯实际是 `glm-5.2`（带横杠），返回 400004「模型不存在」。
- 2026-07-28：`glm5.2` 的 `context_window` 被填成 `205`、`max_output` 漏填（0），导致生成的 opencode.json 缺 `limit.output`，opencode serve 启动校验失败、整个编码工作台打不开（见 `docs/bugs` 相关记录）。

手工填错不仅配置失败，还会**级联拖垮编码工作台**（opencode 启动时校验配置，一个模型配错整个 serve 起不来）。

**目标**：配置 provider 时，平台**直接对接服务商 API 自动拉取真实模型信息**（模型列表 + 各模型的能力参数），用户只需勾选启用，不再手工逐项填写服务 ID / context / output 等。从源头杜绝手滑填错。

## 2. 现状（已取证）

- **配置存储**：`compute_provider`（baseURL、apiKey、enabled）、`compute_model`（name、display_name、context_window、max_output、modality、enabled）。见 `internal/compute/`。
- **配置用途**：`compute/opencode_gen.go` `GenerateOpenCodeConfig` 从这两张表读 enabled provider+model，生成 `opencode.json`（`compute_model.context_window`/`max_output` → `limit.context`/`limit.output`）。
- **增删改入口**：`compute/provider_handler.go` 的 provider/model CRUD handler，变更后调 `refreshOpenCodeConfig` 重写 `/app/opencode.json`。
- **前端**：「算力资源」页面表单手工填 baseURL/apiKey/模型名/参数。
- **已知服务商**：智谱 GLM Coding Plan（`open.bigmodel.cn/api/coding/paas/v4`，模型 glm-5.1/glm-5-turbo）、腾讯混元 MaaS（`tokenhub.tencentmaas.com/v1`，模型 hy3/glm-5.2）。两者都是 **OpenAI 兼容**接口。

## 3. 设计方向（后期细化）

### 3.1 自动拉取模型列表

主流服务商都提供「列模型」接口（OpenAI 兼容标准 `GET /v1/models`）：

- 智谱：`GET https://open.bigmodel.cn/api/coding/paas/v4/models`（Bearer apiKey）
- 腾讯混元 MaaS：`GET https://tokenhub.tencentmaas.com/v1/models`（Bearer apiKey）

新增后端接口（如 `POST /compute/providers/:id/fetch-models` 或新建 provider 时 `?autofetch=true`）：用填入的 baseURL+apiKey 调服务商 `/models`，返回模型 ID 列表，前端展示供勾选。

> **已实测（2026-07-28）两家 `/v1/models` 返回形态**（均 OpenAI 兼容 `{"object":"list","data":[...]}`，但**都不返回能力参数**——无 context/output/reasoning，只能拿到模型 ID 列表）：
>
> - **腾讯混元 MaaS** `GET https://tokenhub.tencentmaas.com/v1/models`：`data[].{id, name, created, status:"online"}`。实测可见模型：`hy3`、`hy3-preview`、`kimi-k3`、`kimi-k2.7-code(-highspeed)`、`glm-5.2`、`minimax-m3`、`deepseek-v4-pro(-flash)`、`hy-mt2-pro`、`hy-3d-3.1`、`kl-video-v3` 等（含视频/3D 多模态，需按 `status`/类型过滤）。
> - **智谱 GLM** `GET https://open.bigmodel.cn/api/coding/paas/v4/models`：`data[].{id, created, owned_by:"z-ai"}`（无 name/status）。实测可见模型：`glm-4.5(-air)`、`glm-4.6`、`glm-4.7`、`glm-5`、`glm-5-turbo`、`glm-5.1`、`glm-5.2`。
>
> **结论**：`/models` 只解决"模型 ID 列表 + 服务 ID 正确性"（彻底根治 `glm5.2` vs `glm-5.2` 这类手滑），**不解决 context/output 填写**——能力参数必须 fallback 到内置默认表（见 3.2）。两家字段结构不一，实现时按 baseURL/host 分支解析。

### 3.2 模型能力参数填充

- 能从 `/models` 拿到 context/output/reasoning 的，自动写入 `compute_model` 对应字段。
- 拿不到的：按服务商+模型名匹配内置默认表（维护一份已知模型默认参数，如 glm-5.2→context 131072/output 8192）；仍无则留空但**不让用户直接保存**——必须填或用默认，避免重蹈 `limit.output` 缺失致 serve 崩溃。
- 复用 `opencode_gen.go` 已有的 limit 防御（漏填补默认），但目标是从源头填对。

### 3.3 连通性校验

保存 provider 前先 `GET /models` 探活：401→提示 key 错；连不上→提示 baseURL/网络；成功→拉模型列表。**配错时当场拦截**，不让错误配置进 DB（当前是配错了也能存，直到 opencode 起不来才暴露）。

### 3.4 非标准服务商兜底

非 OpenAI 兼容 / 无 `/models` 接口的服务商：保留手工填写入口（不强制自动），但加连通性校验（发一个最小 chat 请求探活）。

## 4. 范围与验收（后期实现时定）

- 配 provider（baseURL+apiKey）→ 平台调服务商 `/models` 自动列模型 → 勾选启用 → 自动填 context/output/reasoning。
- 保存前连通性校验，配错当场拦。
- 已知模型默认参数表覆盖智谱/腾讯主流模型。
- 不破坏现有 `GenerateOpenCodeConfig` 与 opencode.json 生成链路。
