# PRD：工作台四问题修复（首页向导 / 附件类型 / 派发幂等 / 任务失败可见）

| 版本 | 日期       | 作者     | 状态               |
| ---- | ---------- | -------- | ------------------ |
| v1.0 | 2026-07-26 | ANP 团队 | 已实现·已验证(.28) |

> 所有根因均在 **10.10.0.28 生产库（deploy_postgres_1 / anp）** 取证，非推断。

## 1. 背景

用户反馈 4 个问题：

1. 首页「开发流程向导」没有数据显示
2. 生成需求规格的附件不支持 md 文件，需支持大部分文件类型
3. 派发编码可连续点击多次，同一需求重复生成编码任务
4. 研发工作台昨日发布的任务全部失败，且看不到失败原因

## 2. 根因定位（含生产证据）

### 2.1 首页向导无数据 —— 非真空，是前端吞错 + 种子错位

- `GET /project-spaces/:id/my-tasks` 实测返回 `HTTP 200 + code:0`，`data.toClaim` 含真实数据（"需求上报系统"等）；DB 有 12 条需求（2 待认领 / 5 开发中 / 2 已交付）。
- **根因①（确定）**：前端 `platform/frontend/app/page.tsx:84-100` 三处裸 `fetch` 不检查 `r.ok` / `r.code`；后端错误响应 `data` 字段 `omitempty`（`httpx/response.go:13`）→ 任何 401/5xx 静默退化成"暂无"卡片。
- **根因②（确定）**：membership 种子 `platform/backend/internal/db/migrate.go:245-249` 把 `user_id` 写成用户名字面量（`admin`/`dev1`/`biz1`），但 `user.id` 实为 `usr_xxx` → `MyTasks` 用 `GetUserByName().ID` 查 membership 永远匹配不到 → 实测 `admin` 的 `roles=[]`，角色过滤（PRD F3）失效。
- 变更侧 `toApprove`/`toRelease` 客观为空（DB 仅 32 rejected + 3 released，无 pending/approved），属正常。

### 2.2 附件不支持 md —— 前端 accept 硬限 + 后端按图片假设

- **根因（确定）**：前端 `requirements/page.tsx:220` 与 `requirements/chat/page.tsx:379` 两处 `accept="image/*"`，浏览器文件选择器直接过滤掉 md 等非图片。
- 后端无扩展名/MIME 白名单，但整条管道把附件当图片：`requirement/service.go:276-311` 把每个附件包成 `image_url` 喂 `glm-4v-flash`（`service.go:334`），`specSystemPrompt` 写死"界面截图/原型图"。即便绕过 accept 传 md，也会被当 image_url 导致模型报错。

### 2.3 派发编码重复提交 —— 后端零幂等 + 前端竞态窗口

- **现场铁证**：需求 `req_f2949bc4f8224b7ea87b` 在 `2026-07-25 15:52:44 / 15:52:48 / 15:53:18` 被连点 3 次，生成 3 条 `code_task` 全 failed。
- **根因①（后端）**：`requirement/service.go:164` `Dispatch` 从不查 `code_task` 是否已有进行中任务；`codetask/store.go` 仅有 `Create/Get/ListByProjectSpace/MarkCompleted/MarkFailed/SetChangeID`，无任何按 source 查重的方法；`code_task.source_id` 无索引无唯一约束（`db/migrations/pg/000001_init.up.sql:145-158`）。
- **根因②（前端）**：`requirements/page.tsx:101-132` `dispatch` 用 `dispatching` state（异步），同 tick 内两次 onClick 都读到旧值 `""` 通过守卫；无 `useRef` 同步锁、无防抖。
- **级联危害**：重复提交 → 多个 opencode 并发操作同一 `repo_dir` → 互相冲突（git lock / 文件竞争）→ 卡死（见 2.4）。

### 2.4 任务失败看不到原因 + 昨日全失败 —— 超时被杀 + 卡死不回写 + 前端藏错

- **看不到原因（前端 bug，确定）**：错误其实已落库 `code_task.output`（`"opencode run 失败: signal: killed"`），但前端 `dev/page.tsx:206-213` 用 `<details>` 默认折叠、summary 写"产出/日志"、文字 `text-green-300`（绿色），且 output 为空时不渲染。9291 字符里错误在最末尾，用户即便展开也要翻到底。
- **昨日全失败真因（确定）**：3 条 failed 的错误**全是** `signal: killed`（SIGKILL）= opencode 编码进程超过 **10 分钟超时**被 `context` 杀掉（`dev/coding.go:144` 硬编码 `context.WithTimeout(ctx, 10*time.Minute)`）。output 显示任务在写 SSH/WinRM adapter、MD5 优化等大模块，10 分钟跑不完。
- **卡 running（确定）**：5 条 `status='running'` 任务 `output` **全空**（len=0）。其中 4 条来自同一需求 `req_802774ec` 在 `05:16:31-05:17:03` 一分钟内重复提交 4 次 → 并发抢同一仓库卡死/panic，goroutine 没走到 `MarkFailed`；另有 `coding.go:76-79` 的 `tasks.Get` 出错直接 `return` 的静默路径也永远卡 running。
- 配置全正常：`zhipuai_api_key` 在、`default_code_model=zai-coding/glm-5.1`、`opencode_config_path=/app/opencode.json` → **非环境/配置问题**。

## 3. 修复方案

### 3.1 问题1：首页向导（修前端吞错 + 修 membership 种子）

| 改动           | 文件                                                            | 内容                                                                                                                       |
| -------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 前端错误可见   | `platform/frontend/app/page.tsx:84-100`                         | 3 处裸 `fetch` 改用 `lib/api.ts` 的 `apiGet`（`!res.ok` 抛错、`code!=0` 显示 `message`）；失败时卡片显示真实错误而非静默空 |
| 修新种子       | `platform/backend/internal/db/migrate.go:245-249`               | `SeedBootstrapMembers` 的 `user_id` 用 `GetUserByName(name).ID` 而非字面量                                                 |
| 修存量错位数据 | 新增迁移 `db/migrations/pg/000016_fix_membership_userid.up.sql` | `UPDATE membership m SET user_id=u.id FROM "user" u WHERE m.user_id=u.name;`（只改 name→id 错位行，避免只修新种子）        |

### 3.2 问题2：附件支持大部分文件类型（放宽 accept + 文本类喂模型）

| 改动                 | 文件                                                          | 内容                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 放宽 accept          | `requirements/page.tsx:220`、`requirements/chat/page.tsx:379` | 改为 `.md,.txt,.markdown,.doc,.docx,.pdf,.png,.jpg,.jpeg,.gif,.webp` 等常用类型                                                                                                                                                         |
| 区分附件类型（前端） | 两处 `onFiles`                                                | 文本类（md/txt/markdown）按 `readAsText` 读内容；图片 `readAsDataURL`；二进制（pdf/doc/docx）仅记录 `{name,type,size}`                                                                                                                  |
| 预览通用化           | 两处预览 UI                                                   | 图片用 `<img>`；文本/二进制用文件名+图标列表（替代纯 `<img>` 破图）                                                                                                                                                                     |
| 字段语义扩展         | `requirement/handler.go`、`service.go`、`conversation/*`      | `images` → `attachments`，每项带 `{kind: image\|text\|file, ...}`；`generateSpec` 分支：图片→`image_url`，文本→拼入 description/prompt（限前 20000 字符），二进制→留档不喂模型；`specSystemPrompt` 文案泛化为"附件（截图/文档/规格稿）" |

### 3.3 问题3：派发编码幂等（后端判重 + DB 兜底 + 前端同步锁）

| 改动                   | 文件                                        | 内容                                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Store 查重方法         | `codetask/store.go`                         | 新增 `CountActiveBySource(ctx, sourceID) (int, error)`：`SELECT COUNT(*) FROM code_task WHERE source_id=$1 AND status='running'`                                                                       |
| Service 判重           | `requirement/service.go:164` `Dispatch`     | `Create` 前调用，>0 返回哨兵错误 `该需求已有进行中的编码任务`                                                                                                                                          |
| Handler 区分冲突       | `requirement/handler.go:291` `DispatchCode` | 重复派发返回 `409 / 40902`（参考同文件 `Assign` 的 409 写法），其余才 500                                                                                                                              |
| DB 部分唯一索引        | 新增迁移 `000017_code_task_unique.up.sql`   | `CREATE UNIQUE INDEX IF NOT EXISTS uq_code_task_running_source ON code_task(source_id) WHERE status='running';`（并发兜底）                                                                            |
| 加索引前清陈年 running | 同迁移前置                                  | `UPDATE code_task SET status='failed', output=COALESCE(output,'')                                                                                                                                      |     | '\n[系统]超时未结束，自动标记失败' WHERE status='running' AND created_at < NOW()-INTERVAL '6 hours';`（避免现存 4 条同源 running 让建索引失败） |
| 前端同步锁             | `requirements/page.tsx:101`                 | 引入 `useRef`，dispatch 入口 `if(inFlightRef.current) return; inFlightRef.current=true`，`finally` 复位；保留 `dispatching` state 做按钮 `disabled`/loading；409 时 toast "该需求已有进行中的编码任务" |

### 3.4 问题4：失败可见 + 超时调大 + 卡死回写（用户已选核心三件）

| 改动         | 文件                   | 内容                                                                                                                                                                   |
| ------------ | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 超时调大     | `dev/coding.go:144`    | `10*time.Minute` → `30*time.Minute`                                                                                                                                    |
| 卡死必回写   | `dev/coding.go` `run`  | 所有异常路径（`tasks.Get` 失败、opencode err、panic）统一走 `MarkFailed`；加 `defer func(){ recover() → MarkFailed("panic: ...") }()` 兜底，杜绝 output 空的永 running |
| 前端失败可见 | `dev/page.tsx:206-213` | `status==='failed'` 时 `<details open>`、summary 改"❌ 失败原因"、文字 `text-red-300`；output 为空时显示"任务异常终止，未产生输出"                                     |

**可选增强（二期，不在本次范围）**：`run` 注入 trace_id（`Submit` 加 `traceID` 参数，从 `handler` `c.GetString("trace_id")` 透传，替换 `context.Background()`）+ `MarkFailed` 同步调 `logsvc.DualLogger` 记 ERROR + `logsvc.QueryFilter` 加 `CodetaskID` 维度，让日志中心也能按任务查。

## 4. 验证计划（.28 端到端，真前端打后端）

按记忆规范，本机不跑功能测试，scp 推 .28 重建容器后用浏览器真验：

1. **部署**：scp 改动文件到 `/opt/anp` → `docker-compose -f deploy/docker-compose.prod.yml up --build -d backend frontend`（前端耗时长，后台跑）。
2. **问题1**：admin 登录首页，"待认领"节点出角标、任务卡显示 2 条真实待办；制造 401（清 token）确认显示错误提示而非空白。
3. **问题2**：需求页上传 `.md` 附件 → 生成规格，确认 md 文本被读入；上传 pdf 确认不报错只留档。
4. **问题3**：同一需求狂点派发 → 仅生成 1 个 codetask，其余弹 409 toast"已有进行中的编码任务"。
5. **问题4**：派发一个复杂编码任务 → 30min 内完成，或超时标记 failed；前端失败任务默认展开、红色显示"signal: killed/超时"；DB 查 `status='running' AND created_at<NOW()-6h` 应为 0。

## 5. 风险与边界

- **部分唯一索引建索引失败**：现存 4 条同源 running 会让 `CREATE UNIQUE INDEX` 冲突 → 迁移内先清理陈年 running（3.3 已含）。
- **30min 超时占用资源**：单任务占 opencode 进程更久，并发任务多时资源挤兑 → 长期需队列化（本期不做，记入风险）。
- **附件文本拼入超上下文**：限制读取前 20000 字符（3.2 已含）。
- **修存量 membership**：`UPDATE ... FROM "user"` 仅改 `m.user_id=u.name` 能匹配的行，不会误伤已是 `usr_xxx` 的正常行。
