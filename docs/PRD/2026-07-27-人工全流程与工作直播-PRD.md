# PRD/设计：人工开发全流程打通 + 员工工作过程直播（里程碑 1）

| 版本 | 日期       | 作者     | 状态   |
| ---- | ---------- | -------- | ------ |
| v1.0 | 2026-07-27 | ANP 团队 | 待评审 |

> 「AI 员工 + 员工工作过程直播」总方案的分阶段交付。**里程碑 1 = 人工**：真人开发者在平台端到端走完开发全流程，且全过程对**三方实时直播可视**。里程碑 2 = AI 员工（身份/派工分叉/AI 执行），设计已定（见 §7 关联），本次不实现。
> 落地优先级（用户既定）：**写完本方案后，先跑通人工全流程**。

## 1. 背景与目标

**两条编码路径（重要澄清，取证见 §2）**：

- `requirements` 页「⚡派发编码」= **AI 黑盒**（`requirement.Service.Dispatch` → `dev.CodingAgent.Submit` → opencode headless），开发者不参与。→ 里程碑 2 的 AI 员工走这条。
- `/workspace` 页 = **人工交互编码**入口（认领 → 注入需求 → opencode iframe → submit/merge）。→ **里程碑 1 的人工流程走这条**。

**目标（里程碑 1）**：

1. 一个真人开发者能在平台端到端走完：**认领需求 → 为该需求开工作台编码 → 提交变更 → 测试（人工验收）→ G3 审批 → 发布 → 需求 `delivered`**。
2. 开发者**全工作过程对三方实时直播**（admin/技术负责人看本空间任意开发者的工作台会话；本人看自己），解决「派工后工作过程不可视」。
3. 派工/认领可**指派给某个开发者**（人），为里程碑 2「指派人/AI 员工」选择器铺路。

**关键约束（决策已定）**：

- **可视粒度 = 直播会话**（用户选）：三方实时看 worker 的编码会话内容（与编码 AI 的对话、工具调用、改了哪些文件），非「事后 transcript」也非「状态卡」。
- **不新建 `worker_session` 表**：里程碑 1 复用 `codews_session + requirement_id` 作为「worker 会话」（YAGNI；统一 `worker_session`/`assignee_type` 留到里程碑 2 接 AI 执行会话时再定）。
- AI 员工（`user.kind=ai`、派工分叉、AI 执行、自主全流程）**不在本次范围**。

## 3. 设计

### 3.1 核心抽象：Worker Session（里程碑 1 先接人）

「一个 worker 干一个需求 = 一个 session；三方直播 = 实时读这个 session 的内容流。」里程碑 1 里 worker = 真人开发者，session = **绑定了 requirement_id 的 codews 工作台会话**。这套抽象里程碑 2 原样接纳 AI 员工（AI 执行也产出一个可流式读取的会话）。

### 3.2 codews 工作台绑定需求（堵阶段 2 缺口，为可视奠基）

- **迁移 `000020`**：`codews_session` 加 `requirement_id TEXT`（可空，兼容存量与 application 页开工作台的老入口）+ 索引 `(project_space_id, requirement_id)`。
- **会话键扩展**：`codews/manager.go:120` 会话键由 `appID:userID` 改为 `appID:userID:reqID`（reqID 空时退化为老键，兼容老入口）→ **一需求一会话，杜绝多需求串台**；端口分配（9400-9450）已支持多会话。
- **透传 reqID**：`appdeploy/handler.go:172-203` `Workspace` body 增 `requirement_id`；`Manager.Ensure`/`StartSession` 收 reqID，写进 `codews_session.requirement_id`（`session_store.go` INSERT/Upsert 加列）。
- **前端**：`workspace-frame.tsx` `onStartReq` 认领开发时把 `selectedReq` 作为 `requirement_id` 带进 `/workspace`（目前只进 `InjectRequirement` 文本，改为落库）；刷新/重开按 `requirement_id` 恢复会话与关联。
- **`InjectRequirement`**（`appdeploy/handler.go:376-409`）保留（仍是「把需求 prompt 注入会话」的便捷动作），但绑定不再依赖它。

### 3.3 工作过程直播流（堵阶段 7 缺口）

新增 `internal/worker/` 包（worker 会话观察层；里程碑 2 AI 执行会话也并入此包）：

- **读源已有**：`codews/manager.go:314/319` SessionMessages（opencode 活跃会话快照）、`codews/transcript.go` TranscriptReader（claude/codex jsonl / opencode 磁盘兜底，按 repoDir+sessionId 归一化）。**本里程碑不新造读源**。
- **直播端点（SSE）**：`GET /project-spaces/:id/requirements/:rid/worker-session/stream`
  - 后端：按 `requirement_id` 查 `codews_session` 取当前会话（tool/repo_dir/session_id），开 SSE，**每 ~1–2s 经 TranscriptReader/SessionMessages 拉增量消息推送**（`event: message`，去重按消息序号/时间）；会话结束时推 `event: done`。
  - 诚实的实时性：**近实时（1–2s 轮询驱动的 SSE）**，对人眼足够「直播」；真推送（WS）YAGNI，留二期。
- **历史端点**：`GET /project-spaces/:id/requirements/:rid/worker-session/messages?since=` —— 分页/增量拉历史（复用 TranscriptReader，免入库，同绩效 PRD 取舍）。
- **会话元信息**：`GET /project-spaces/:id/requirements/:rid/worker-session` —— 当前 worker（user）、tool、status、started_at、message_count。
- **降级**：会话不活跃（工作台关）→ stream 立即 `event: idle`；transcript 解析失败 → 历史接口返回已解析部分 + 降级提示（同绩效 PRD 容错）。

### 3.4 人工全流程收口

- **审批 RBAC（小，堵阶段 5）**：`change/handler.go:62/86` Approve/Reject 加 `auth.Allowed("change.approve", ...)`（role: gatekeeper/admin，或同 deploy.prod 的权限分离口径），禁止自批（reviewer != author）。与最近「部署权限分离 test/prod」方向一致。
- **指派给人 UI（补阶段 1）**：`requirements/page.tsx` Requirement 类型补 `assignee` 字段；加「认领 / 指派给\<开发者\>」入口（后端 `requirement/handler.go:247-258` 已就绪，前端接选择器）。`/workspace` 抽屉的「认领开发」保留。
- **端到端 dogfood（必做，见 §4 AC1）**：在 `.28` 用真人账号走一遍 `/workspace` 全链路，确认 `requirement` 真到 `delivered`、`codews_session.requirement_id` 落库、三方直播可见。

### 3.5 数据模型（迁移 `000020`）

```sql
ALTER TABLE codews_session ADD COLUMN requirement_id TEXT;
CREATE INDEX IF NOT EXISTS idx_codews_session_req
  ON codews_session (project_space_id, requirement_id);
```

- 只加 `requirement_id`（里程碑 1 唯一新增列）。`assignee_type`/`worker_id`/统一 `worker_session` 表 **不加**，留里程碑 2。
- `user.kind`（human/ai）**不加**，留里程碑 2。

### 3.6 API（v1，project_space 隔离，走 AutoRequire）

| 方法 | 路径                                                            | 说明                                                        | 守卫         |
| ---- | --------------------------------------------------------------- | ----------------------------------------------------------- | ------------ |
| POST | `/project-spaces/:id/workspace`                                 | body 增 `requirement_id`（可空）                            | 登录         |
| GET  | `/project-spaces/:id/requirements/:rid/worker-session`          | 当前 worker 会话元信息                                      | admin / 本人 |
| GET  | `/project-spaces/:id/requirements/:rid/worker-session/messages` | 历史/增量消息                                               | admin / 本人 |

`worker-session/*` 守卫：admin（及二期技术负责人）看本空间任意；本人（`requirement.assignee` == 自己或会话 `user_id` == 自己）看自己。

### 3.7 前端

- `requirements/page.tsx`：Requirement 类型补 `assignee`；加「认领 / 指派给」入口。
- 新「**工作直播**」面板（`/workspace` 详情或团队看板内）：选中需求 → SSE 订阅 `worker-session/stream`，流式渲染 worker 编码会话（对话 + 改动文件），复用绩效 PRD 的会话聊天渲染（`performance` 页已有）；标注 worker 身份（人）。
- `workspace-frame.tsx`：`onStartReq` 把 `requirement_id` 带进 `/workspace` 落库；按 `requirement_id` 恢复会话。

### 3.8 权限

沿用绩效 PRD 可见范围：admin 看本空间全员直播；本人看自己。二期加「技术负责人」角色。审批走 §3.4 RBAC。

## 6. 风险与边界

- **SSE 后端轮询开销**：每个旁观者一条 SSE、后端每 1–2s 拉一次会话消息。MVP 假定单容器、少量并发旁观者（同绩效 PRD P2 标注）；多旁观者订阅同一会话可共享一个拉取 goroutine。
- **opencode 活跃才可直播**：开发者工作台关闭 → 会话不活跃 → stream 转 `idle`；历史仍可读（TranscriptReader 读磁盘）。可接受。
- **会话键变更兼容**：老入口（application 页开工作台，不带 reqID）退化为 `appID:userID:` 键，行为不变；存量 `codews_session` 行 `requirement_id` 为 NULL，不参与按需求查询。
- **transcript 解析稳定性**：随 CLI 版本可能变 → 复用绩效 PRD 的容错（未知字段忽略、content 双形态兼容），失败降级不阻断。
- **审批 RBAC 角色口径**：`change.approve` 授权哪些角色（gatekeeper/admin/技术负责人）实现时与现有 `auth.AutoRequire` 白名单对齐；MVP 先 gatekeeper/admin。
- **dogfood 前提**：`.28` 上智谱 key（`zhipuai_api_key` + 兼容端点，git log a5167a7 已修 agent-runtime 走智谱 anthropic 端点）可用；opencode 工作台在容器可跑（既有能力）。
