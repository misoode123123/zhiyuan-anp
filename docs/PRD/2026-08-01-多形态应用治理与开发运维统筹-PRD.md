## 0. 定位

ANP 是**开发者平台**，不是单纯的运维/部署平台。核心价值 = **研发过程落地**：把任意类型的应用（web/服务、bot、桌面软件、小程序、移动端、CLI）从想法 → 需求 → 设计 → 编码 → 审查 → 测试 → 发布 → 运维 → 持续迭代，**整条研发链在 ANP 内完成**。部署/运维是这条链的尾端环节，不是 ANP 的全部。

本 PRD 从研发全生命周期视角，确立多形态应用如何在 ANP 里被研发、构建、发布、运行。承载用 Docker + 网络 + 网关，**不上 K8s**。

> 前几版 PRD 偏了——把重心放在 app-space/两态/依赖供给/产物分发（研发产出物的"承载与发布"）。本次纠偏：**研发主轴在上，承载层只是主轴里"构建·发布·运行"环节的规则**。

---

## 1. 起因

客服机器人事件（导入部署失败 → Redis 崩溃 → 根因是**导入 zip 包装目录未剥**致源码嵌套 → buildpack 误判）暴露：研发链的"构建/运行"环节对多形态应用支持不足。已处置：flatten 修复上线（`86fb776`）、dockerSlug 修复上线（`1657546`）、停崩溃副本、bot 走自带 compose。本 PRD 把视野从"部署"扩到"整个研发链对多形态应用的支撑"。

---

## 2. 研发主轴（核心，全应用类型共享）

```
需求 → 设计 → 编码(opencode) → 代码审查 → 测试(qa) → 安全扫描
   → 变更/审批(闸门) → 构建 → 发布 → 运维 → 审计
        ↑                                                    │
        └────────────────── 持续迭代 ─────────────────────────┘
```

每个环节对应 ANP 已有板块（开发者平台的地基，全类型共用）：

| 研发环节       | ANP 板块/能力                         |
| -------------- | ------------------------------------- |
| 需求           | 需求工作台                            |
| 设计           | 需求/设计文档（docs 随仓库版本管理）  |
| 编码           | 研发工作台（opencode，`CodingAgent`） |
| 代码审查       | 变更/审批（变更闸门 `HasApproved`）   |
| 测试           | 测试与质量中心（qa 自动验收）         |
| 安全扫描       | 安全与合规中心（`artifact_scan`）     |
| 变更/审批      | 变更闸门 + RBAC 部署权限分离          |
| 构建/发布/运行 | **承载层（§4）+ 运维中心**            |
| 运维           | 运维中心（监控/stop-start/日志/回滚） |
| 审计/配额      | 变更记录、配额、规则治理中心          |

**所有应用类型共用这条主轴**——研发环节的差异集中在末端的"构建/发布/运行"三步，前面（需求→…→审批）完全一致。

---

## 3. 各应用类型在研发主轴上的表现

### 3.1 共享环节（全类型一致）

需求 / 设计 / 编码(opencode) / 代码审查 / 测试 / 安全扫描 / 变更审批 —— **所有类型走 ANP 同一套**，不因应用类型而异。这是"开发者平台"统一体验的来源。

### 3.2 差异化环节：构建 / 发布 / 运行（因类型而异）

| 类型                 | 构建                                    | 发布                                           | 运行/运维                                             |
| -------------------- | --------------------------------------- | ---------------------------------------------- | ----------------------------------------------------- |
| web/service          | 镜像 build                              | app-space 部署容器 + appgw URL                 | 在 ANP 容器运行，HTTP 探活                            |
| headless(bot/worker) | 镜像 build                              | app-space 部署无 URL                           | 在 ANP 容器运行，进程/外连健康                        |
| 桌面软件             | 多平台交叉编译(win/mac/linux·x64/arm64) | 打包签名→artifact store→下载页/自动更新源/商店 | **运行在用户电脑**（ANP 外）；ANP 管版本/自动更新推送 |
| 小程序-客户端        | miniprogram-ci/wx devtools 编译上传包   | 微信平台：上传体验版→审核→发布                 | 运行在微信（ANP 外）；ANP 编排上传+留版本             |
| 小程序-后端          | 镜像 build                              | app-space 部署                                 | 在 ANP 容器运行                                       |
| 移动端               | 构建 apk/ipa(多架构)                    | artifact store→商店上架/内测                   | 运行在用户手机（ANP 外）                              |
| CLI                  | 多平台 go build/cargo                   | artifact store→下载页                          | 运行在用户机器（ANP 外）                              |

> **关键认知**：只有 web/service/headless/后端这类"在 ANP 容器里运行"；桌面/小程序客户端/移动/CLI 的**研发全链都在 ANP**，但**最终运行在用户设备**——ANP 管的是它们的"研发+构建+发布+版本"，不是"托管运行"。研发过程一样完整落地。

## 4. 承载层（构建·发布·运行的规则，服务研发主轴）

承载层回答研发主轴里"构建物长什么样、跑在哪、怎么互通、怎么分发"。它是主轴的子题，不是主角。

### 4.1 运行态承载：app-space（应用 = 网络 + 组件集）

每个**在 ANP 运行的**应用 = 一个隔离 Docker 网络 + 一组类型化组件容器（`web`/`api`/`headless`/`data`(pg/redis/milvus)/`middleware`）。应用内服务名直连，应用间默认隔离、HTTP 走 appgw、内部互通走显式 peering。整栈生命周期（部署/停/删/版本/回滚）。

### 4.2 产物态承载：构建 → 存储 → 分发

客户端类型（桌面/移动/CLI/小程序客户端）的产物链：多平台构建（在构建容器里跑，`BuildConfig.build_image/build_command`）→ artifact store（`artifact_storage_local`）→ 分发渠道（下载页 / 自动更新源 `latest.yml` / 微信 CI 上传 / 商店上架）。ANP 已有构建+存储骨头，**分发渠道是待补主件**。

### 4.3 两态模型

一个应用可有运行态（app-space）和/或产物态（产物链）：

- 纯 web 服务：仅运行态。
- 纯桌面工具：仅产物态。
- 小程序 / 带云后端的桌面软件：**两态都有**（客户端产物 + 后端运行态）。

### 4.4 依赖供给与互通

- **依赖供给三策略**：`dedicated`（每 app 独立实例，默认，PG 已是）/ `shared`（ANP 级共享 + db号/前缀隔离，**已定：提供作为降本选项**）/ `bind-existing`（绑定部署机已有服务，导入项目最常见）。应用声明依赖 → ANP 注入连接 env（扩 `DATABASE_URL` 范式到 `REDIS_ADDR` 等），应用侧读 env、无需 host 网络。
- **网络策略**：bridge 默认；`host` 按应用+审批+角色门禁，不默认开。
- **应用间互通**：HTTP 走 appgw；内部服务走显式 peering（opt-in，默认 deny，留痕）。

---

## 5. 治理脊柱（横切研发主轴 + 承载层）

不分应用类型、不分两态，统一一套：RBAC（部署权限分离 `app.deploy.test/prod`）、变更闸门（`HasApproved`）、配额、版本/回滚、监控/日志/告警、stop/start、安全扫描（`artifact_scan`）、自动验收（qa）、变更审计。**全部已有**，作用域覆盖整栈与产物发布。

## 6. 与现有架构契合（扩展非替换）

| 现有设计                                                  | 角色                                       |
| --------------------------------------------------------- | ------------------------------------------ |
| 需求/研发/测试/安全/规则/运维 各板块                      | 研发主轴的承载者（本 PRD 主线即此）        |
| 每项目独立 PG                                             | per-app 数据组件范例 → 推广到 redis/milvus |
| appgw 网关                                                | 对外入口 + 应用间 HTTP 路由                |
| 不上 K8s                                                  | per-app 网络 = Docker network              |
| `BuildConfig`/`ArtifactStore`/`Desktop/Mobile/CLIBuilder` | 产物态骨架，补分发渠道                     |
| RBAC 部署权限分离 / 变更闸门                              | 作用域升级到整栈/产物发布，规则不变        |
| `CodingAgent`/opencode                                    | 编码与导入适配入口                         |

## 7. 落地路线图（按研发链补强，增量）

| 阶段            | 内容（补强研发链对多形态应用的支撑）                                                                                                      | 状态      |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| **近期**        | flatten 修复（导入不嵌套）；dockerSlug 修复；编码适配（opencode）；停客服机器人崩溃副本                                                   | ✅ 已完成 |
| **中期-运行态** | ① opencode 导入适配(改应用代码+经ANP受控供给缺失服务) ② 依赖声明+连接注入(REDIS_ADDR 等) ③ headless 运行(无端口/进程健康) ④ host 网络门禁 | ⏳ 待立项 |
| **中期-产物态** | ⑤ 多平台构建矩阵 ⑥ artifact 分发：下载页 + 自动更新源                                                                                     | ⏳ 待立项 |
| **远期**        | ⑦ 完整 app-space(多组件栈+dedicated/shared 供给+appgw应用间路由+peering) ⑧ 小程序微信 CI 编排 ⑨ 移动商店上架 ⑩ 多形态研发看板             | ⏳ 愿景   |

中期各项独立，建议顺序：opencode 导入适配 → 依赖注入 → headless → 多平台构建+分发 → host 门禁。

## 8. 风险与取舍

| 风险                                     | 应对                                                              |
| ---------------------------------------- | ----------------------------------------------------------------- |
| host 网络削弱隔离                        | 不默认；按应用+审批+角色门禁；优先 bind 可达实例                  |
| dedicated 资源成本                       | 按声明供给 + shared 降本选项 + 配额                               |
| 共享中间件多租户隔离                     | db号/namespace/前缀 + 配额 + 删除清理                             |
| 依赖注入密钥管理                         | env 注入不落日志；复用 pgsupply 范式，后续接 vault/KMS            |
| 客户端分发渠道碎片                       | 抽象"分发渠道"接口，按 app_kind 选配                              |
| 多平台构建矩阵成本                       | 按需启用平台；交叉编译优先于多 OS runner                          |
| 研发链对客户端类型"运行不在 ANP"的认知差 | UI 明示该类型"研发在 ANP、运行在用户侧"；运维环节按类型差异化展示 |

## 9. 待决议项

1. **app-space 组件粒度**：web/api/headless/data/middleware 这套，还是更粗/更细？
2. **依赖供给默认**：导入项目默认 `bind-existing` 还是 `dedicated`？（建议 bind + 提示）
3. **host 网络门禁**：复用变更闸门加网络策略字段，还是单设审批？
4. **产物态优先级**：先"多平台构建+下载/自动更新"（桌面/CLI 通用）还是先"小程序微信 CI"？（建议先通用）
5. **小程序是否本期范围**：它两态都有、依赖微信侧能力，是否放远期？
6. **✅ 已定 — shared 中间件**：提供 ANP 级共享 redis/milvus 降本（dedicated 默认 + shared 可选）。
