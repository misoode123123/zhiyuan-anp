## 0. 一句话主张

ANP 不要把所有应用硬塞进"单个 web 容器 + 端口 + URL"的模子——**按应用形态分类纳管，挂同一条治理脊柱**，开发运维就是一条线。今天的客服机器人事件，本质就是"一个多服务、外发型、按 host 网络设计的应用，被塞进了 web 模子"。

## 1. 当前问题（实证：客服机器人事件）

### 1.1 事件复盘

导入「客服机器人」（企微智能助手 yxt_eino_v2，Go 写的**长连接外发机器人**）后点"部署"，ANP 构建出的容器崩溃重启死循环：

```
bot exit: 初始化 redis: dial tcp 127.0.0.1:6381: connect: connection refused
```

逐层诊断出的真实链路（每层都推翻了上一层假设）：

| 层       | 现象                               | 真因                                                                                                                                           |
| -------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 构建     | 容器起不来                         | 不是构建失败，镜像构建成功（v8）                                                                                                               |
| 运行     | Redis 连接拒绝 → exit 1 → 重启循环 | bot 跑在 **bridge 容器**里，`127.0.0.1` 指向容器自身，够不到宿主机 Redis                                                                       |
| 设计     | 为何 `127.0.0.1`                   | bot 原本按 **host 网络 + docker-compose** 设计（compose 里 `network_mode: host`，依赖 redis/milvus/pg 全在 localhost）                         |
| 元数据   | ANP 构建的是 nginx 不是 Go         | buildpack 把它误判 static 生成了 nginx Dockerfile                                                                                              |
| **根因** | buildpack 为何误判                 | **导入的 zip 带顶层包装目录 `yxt_eino_v2 - 客服机器人/`，`ImportFromZip` 没剥**→ 源码嵌在子目录 → 仓库根没 `go.mod` → `detectType` 兜底 static |

### 1.2 已处置（本次闭环）

- **临时解封**：停掉 ANP 那条必然崩溃的 bridge 副本容器；bot 本就用自带 docker-compose 在 .28 上正常跑（`yxt-bot`，host 网络，已连企微，是主实例）。
- **治本（已上线）**：`ImportFromZip` 解压后剥单一包装目录（`flattenSingleWrapper`，commit `86fb776`，已 push + scp + .28 重建 backend 生效，+4 子用例单测）。以后导入不再嵌套。
- **决策**：不单独造"部署分析/适配"功能——导入后用现有 AI 编码能力（opencode）做适配，改动走现有「变更登记→审批→部署」。

### 1.3 暴露的系统性缺口

| 缺口           | 表现                                                             | 归属维度 |
| -------------- | ---------------------------------------------------------------- | -------- |
| 应用模型单一   | 只有"web 容器+端口+URL"一种部署语义；bot/多服务应用无处安放      | 形态分类 |
| 中间件供给单一 | 只给应用配 PG（`DATABASE_URL`）；Redis/Milvus/MQ 无供给/绑定机制 | 依赖供给 |
| 网络模式单一   | 恒为 bridge，无按需 host 网络能力                                | 网络策略 |
| 导入不分析     | 原样搬代码，不识别形态/依赖/网络需求（flatten 只解了嵌套这一项） | 适配入口 |

> 注意：**治理脊柱是齐的**——RBAC 部署权限分离（dev 可 test、prod 走闸门）、变更闸门、配额、版本/回滚、监控、审计、安全扫描、自动验收都有。缺的是"应用形态模型"，让脊柱挂不住非 web 应用。

## 2. 问题本质

ANP 的应用抽象隐含一个假设：**应用 = 一个监听 HTTP 端口的 web 容器**。于是部署 = build 单容器 → `-p host:internal_port` → 给 URL。这个假设覆盖了 demo/简单 web，但三类真实应用被排斥在外：

1. **外发型/常驻型服务**（bot、worker、daemon、定时任务）：长跑、**主动外连**、不监听 HTTP、没有"页面"。健康 ≠ HTTP 200，而 = 进程存活/外部连接成功。
2. **多服务应用**（带 compose 的全栈）：一个应用 = bot + redis + milvus + pg + …，是一**组**容器，不是单容器。
3. **host 网络依赖型**：按 host 网络设计（config 里 `127.0.0.1` 访问本机中间件），bridge 容器内 `127.0.0.1` 够不到。

客服机器人三样全占。**解法不是给它打补丁，而是让 ANP 的应用模型能表达这些形态，且共用同一条治理脊柱。**

---

## 3. 目标与非目标

**目标**

- ANP 能按形态分类纳管应用：web/service（HTTP+URL）、headless（bot/worker，无 URL）、stack（多服务）。
- 应用能声明外部依赖（Redis/Milvus/PG/MQ…），ANP 供给或绑定，并把连接信息注入容器（复用 `DATABASE_URL` 注入范式）。
- 网络模式可按应用选择（bridge 默认 / host 受控），host 走审批+角色门禁。
- 导入后能识别形态/依赖/网络需求（轻量分析 + 编码适配），产出"部署适配清单"。
- 无论哪种形态，dev→ops 都是**同一条受治理流水线**（编码→构建→测试→闸门→上线→运维→审计），只是"部署/健康/暴露"语义按形态变。

**非目标（YAGNI）**

- ❌ 不造重型"部署分析/适配引擎"（已决策：复用 opencode 编码能力适配）。
- ❌ 不上 K8s（架构已定：每项目独立 PG、appgw 网关、容器直跑）。
- ❌ 不全自动：所有 prod 仍走变更闸门 + RBAC，host 网络仍需审批。
- ❌ 本期不做项目级（Project L2）批量治理，仍以 Application 为单位。

## 4. 治理方案：四维度

### 4.1 形态分类纳管（扩 `app_kind`）

新增/细化 `app_kind`，每种形态有独立的"部署语义 + 健康判定 + 对外暴露"：

| app_kind          | 代表              | 部署                           | 健康判定                                 | 对外暴露                    |
| ----------------- | ----------------- | ------------------------------ | ---------------------------------------- | --------------------------- |
| `web` / `service` | web 服务、API     | 单容器 + 端口映射（现状）      | HTTP 探活 internal_port                  | URL（appgw 路由）           |
| `headless`（新）  | bot/worker/daemon | 单容器，无端口映射需求         | 进程存活 / 自定义 healthcheck / 外连成功 | 无 URL（或仅 metrics 端口） |
| `stack`（新）     | 多服务全栈        | 部署一组容器（compose 服务集） | 各容器各自健康                           | 入口容器映射端口（可选）    |

- `web/service` 完全沿用现状。
- `headless`：复用现有 `Deployer.Deploy`，跳过端口映射与 URL；健康判定从"HTTP 200"改为"`docker inspect` State.Running + 可选自定义 healthcheck"。客服机器人即此形态（健康 = 连上企微 WS）。
- `stack`：`appdeploy_instance` 升级为表达"一组容器"（或新增 `appdeploy_stack_service` 子表），部署 = `docker compose up` 该应用的服务集，版本 = 整组版本。

形态可由导入分析/编码适配推断，也可由创建/导入向导显式选。

### 4.2 依赖中间件供给（三策略，按成本/隔离取舍）

应用**声明依赖**（来自导入分析或编码适配，结构化：`{kind: redis, ...}`），ANP 据策略供给或绑定，并把**连接信息注入容器环境变量**（完全复用今天 `DATABASE_URL` 的注入范式，扩展到 Redis/Milvus 等）。

| 策略             | 做法                                                        | 适用                         | 取舍                   |
| ---------------- | ----------------------------------------------------------- | ---------------------------- | ---------------------- |
| **平台供给**     | 按 app 动态起一个实例（PG 已是此模式：每项目独立 PG）       | 需强隔离的核心依赖           | 隔离强、成本高、运维重 |
| **共享平台服务** | 一个 ANP 级 Redis/Milvus，多应用用 db 号/namespace/前缀隔离 | 通用中间件                   | 省、需配额+隔离+清理   |
| **绑定已有服务** | 应用声明依赖 → 指向部署机已有服务 → ANP 注入连接配置        | 导入项目最常见（服务已在跑） | 最省；须校验可达+权限  |

客服机器人 = 典型"绑定已有"：声明 `{redis, milvus, pg}` → 绑定 .28 的 `yxt-redis:6381`/`yxt-milvus:19530`/`yxt-pgsql:5434` → ANP 注入 `REDIS_ADDR`/`MILVUS_ADDR`/`PG_*` → bot 在 bridge 容器里经宿主 IP 连上。

> 关键设计：**应用侧优先读环境变量**（已是行业惯例，Go viper/Node dotenv 都支持）。编码适配时让 config 走 env 覆盖（`${REDIS_ADDR}` 或读 `REDIS_ADDR`），ANP 注入即可——无需 host 网络。

### 4.3 网络策略（受控）

- **bridge 默认**（隔离、端口可控、安全默认）。
- **host 网络 = 按应用、需审批、限角色的能力**，不默认开。直接呼应"权限/风险"担忧：host 网络削弱隔离，必须过闸门 + 仅特定角色可用，且在应用详情显式标注风险。
- **多服务 stack 内部**通信用 compose 内网服务名（如 `redis:6379`），无需 host 网络。
- 当应用依赖的服务**只绑 loopback**（容器够不到）时，平台提示：要么改服务监听 `0.0.0.0`，要么走 host 网络（审批），要么换"绑定可达实例"。

### 4.4 适配入口（导入即理解）

- **编码适配（已确立）**：导入后用编码工作台/派发编码（`CodingAgent` → `opencode run --auto`）下"适配 ANP"指令：改 config 走 env、修 Dockerfile、调整监听地址。改动走变更审批。
- **导入 flatten（已上线）**：剥包装目录，保证"仓库根=项目根"。
- **buildpack 分类**：仓库根有 `go.mod`/`package.json`/… 时正确识别（detectType 本就正确，flatten 修复后能命中）；应用自带 Dockerfile 优先用。
- **轻量导入分析（中期）**：扫描产出"形态猜测 + 依赖清单 + 网络需求 + 与 ANP 模型差异"的结构化提示，供编码适配与人工参考（**规则提事实为主，不造重型引擎**）。

## 5. 统一开发运维脊柱（dev → ops，一条线，不分形态）

```
开发 → 构建 → 测试(test) → 变更闸门 → 上线(prod) → 运维 → 审计/配额
 │       │       │            │           │        │         │
opencode flatten  dev 部署    RBAC        promote   监控      变更记录
适配    +build   按形态判健康  +HasApproved +闸门     stop/start 安全扫描
        pack     (HTTP/进程/   (部署权限    (prod     日志 回滚  自动验收
                 各容器)       分离)        专属)     qa         quota
```

- **所有形态共用这条脊柱**：RBAC（`app.deploy.test/prod`）、变更闸门（`HasApproved`）、配额、版本/回滚、监控（`server_monitor`/metrics）、stop/start、日志、安全扫描（`artifact_scan`）、自动验收（qa）——**全部已有**，无需重造。
- **按形态差异化的只有三处**：部署方式（单容器 / 无端口 / stack）、健康判定（HTTP / 进程 / 各容器）、对外暴露（URL / 无 / 入口容器）。
- 这样 bot、多服务栈、web 都走同一条受治理流水线，治理面（谁能部署、过没过闸门、配额、审计）完全一致。

## 6. 与现有架构契合（扩展，非替换）

| 现有设计（已定）                   | 本方案如何契合                                                     |
| ---------------------------------- | ------------------------------------------------------------------ |
| 每项目独立 PG 实例（无 pgbouncer） | "平台供给"策略即此模式的泛化（PG 已是、Redis/Milvus 可按需）       |
| appgw 网关统一入口                 | web/service 形态的 URL 经 appgw 路由不变；headless 无 URL 不走路由 |
| 不上 K8s                           | 全程 docker/compose，不引入新编排                                  |
| 部署权限分离（RBAC 按 env）        | 新形态沿用同一 RBAC 矩阵；host 网络叠加额外审批                    |

| `DATABASE_URL` 注入（pgsupply）    | 扩展为通用"依赖连接注入"（REDIS_ADDR 等）                          |

## 8. 风险与取舍

| 风险                                | 应对                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| host 网络削弱隔离                   | 不默认开；按应用 + 审批 + 角色门禁；详情页标注风险；优先用"服务改监听 0.0.0.0 / 绑定可达实例"替代 |
| 共享中间件的多租户隔离              | namespace/db 号/前缀隔离 + 配额 + 应用删除时清理其数据                                            |
| 依赖注入的密钥管理                  | 连接串含密码，注入走 env（不落日志/不回显）；复用现有 pgsupply 的凭证管理范式，后续接 vault/KMS   |
| 形态误判（把 web 认成 headless 等） | 分析只产"提示"，最终形态可由向导/人工确认；headless 与 web 健康判定可兼容（先 HTTP 再进程）       |
| stack 形态复杂度                    | 放远期，先以 headless + 依赖注入覆盖大部分（如客服机器人 = headless + 绑定依赖，不需 stack）      |

## 9. 验收用例（客服机器人为样本）

以中期完成后的能力，客服机器人在 ANP 内的预期形态：

1. **导入**：zip 带 `yxt_eino_v2 - 客服机器人/` 包装 → flatten 剥掉 → 仓库根是 Go 项目 → buildpack 识别 go（或用自带 Dockerfile）。
2. **导入分析**：识别 `app_kind=headless`（无 HTTP 服务，长连接外发）、依赖 `{redis, milvus, pg}`、网络需求"原设计 host 但可改 bridge+host IP"。
3. **依赖绑定**：声明三项依赖 → 绑定 .28 已有 `yxt-redis:6381`/`yxt-milvus:19530`/`yxt-pgsql:5434` → ANP 注入 `REDIS_ADDR=10.10.0.28:6381` 等。
4. **编码适配**：opencode 把 config 改为读 env（或直接改地址）、Dockerfile 补 `COPY config.yaml` → 走变更审批。
5. **部署（test）**：headless 形态，无端口映射；bridge 容器经宿主 IP 连上 redis/milvus/pg；健康 = 连上企微 WS（非 HTTP）。
6. **运维**：ANP 显示 running（无 URL）、可 stop/start、监控、版本回滚、自动验收（按企微连通性）。
7. **上线（prod）**：过变更闸门 + RBAC，prod 实例同样跑通。

> 即：中期做完，客服机器人无需 host 网络、无需 stack，**headless + 依赖绑定 + 编码适配**即可在 ANP 内正经纳管。

## 10. 待审核的决议项

1. **形态分类粒度**：`headless` 是否要再细分（bot/worker/cron），还是统一一类？（建议统一 headless，按需再拆。）
2. **依赖供给默认策略**：导入项目默认走"绑定已有"，还是"平台供给"？（建议默认绑定已有 + 提示，平台供给按需。）
3. **host 网络门禁**：放在变更闸门里统一批，还是单独的"网络策略审批"？（建议复用变更闸门，加网络策略字段。）
4. **stack 形态优先级**：是否如路线图放远期？（客服机器人等多数 case 用 headless+依赖绑定即可覆盖，stack 可后置。）
