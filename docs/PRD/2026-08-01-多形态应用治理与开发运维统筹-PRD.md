## 0. 愿景

**ANP 是一个"以应用为边界、两态纳管、AI 辅助适配、统一治理"的多应用托管平台。** 每个应用 = 一个隔离的 app-space（运行态：网络+组件容器）+ 一条产物链（产物态：构建→存储→分发）；所有应用类型（web/服务/bot/小程序/桌面/移动/CLI）共用同一条 dev→ops 治理脊柱。不上 K8s，用 Docker + 网络 + 网关实现。

---

## 1. 起因与问题（客服机器人事件）

导入「客服机器人」（企微外发机器人，Go）后部署崩溃死循环（Redis `127.0.0.1:6381` connection refused）。逐层诊断真因：bot 按 **host 网络 + docker-compose** 设计（依赖 redis/milvus/pg 在 localhost）→ ANP 把它塞进 **bridge 单容器**且只给 PG → 崩；外加 **导入 zip 包装目录未剥**→ 源码嵌套 → buildpack 误判 static。

**已处置**：flatten 修复已上线（`flattenSingleWrapper`，commit `86fb776`，已部署 .28）；停掉 ANP 崩溃副本；bot 走自带 compose 正常服务；决策不造重型适配引擎、复用 opencode 编码适配。

**暴露的系统性缺口**：

| 缺口           | 表现                                                   |
| -------------- | ------------------------------------------------------ |
| 应用模型单一   | 只有"web 容器+端口+URL"，bot/多服务/客户端应用无处安放 |
| 中间件供给单一 | 只配 PG，Redis/Milvus 无供给/绑定                      |
| 网络模式单一   | 恒 bridge，无按需 host                                 |
| 导入不分析     | 原样搬代码，不识别形态/依赖/网络                       |
| 客户端类型缺位 | 桌面/移动/小程序只有构建骨架，无完整"开发→发布"链      |

> 治理脊柱（RBAC 部署权限分离、变更闸门、配额、版本/回滚、监控、审计、安全扫描、自动验收）**已齐**，缺的是"应用模型能表达多样性"。

---

## 2. 核心抽象：app-space（应用 = 网络 + 组件集）

**每个应用 = 一个隔离的 app-space = 一个 Docker 网络 + 一组类型化组件容器。**

- 组件类型：`web`(HTTP+URL) / `api` / `headless`(bot/worker，无URL) / `data`(pg/redis/milvus) / `middleware`。每类有独立的"部署语义+健康判定+暴露规则"。
- 应用**声明**自己的组件（清单，来自导入分析+编码适配），ANP 按声明供给——不是每个应用都塞 redis。
- **应用内**：同网络按服务名直连（`api`→`redis:6379`），与 docker-compose 一致。
- **应用间**：默认网络隔离；HTTP 走 appgw 网关；内部互通走显式 peering（opt-in，留痕）。
- **整栈生命周期**：部署/停/删/版本/回滚都以 app-space 为单位。

> 原 PRD 的 `app_kind` 降级为 **app-space 内的组件类型**；`stack`/`headless` 不再是"另类形态"，而是组件组合的典型。

---

## 3. 两态模型：运行态 + 产物态（覆盖所有应用类型）

app-space 覆盖**运行态（服务端）**；小程序/桌面/移动/CLI 是**客户端产物**，需要**产物态（构建→存储→分发）**。一个应用可有其一或两者：

| 应用类型     | 运行态(app-space) | 产物态(构建→分发) | 典型                         |
| ------------ | ----------------- | ----------------- | ---------------------------- |
| web/service  | ✅ 容器+URL       | —                 | 网站、API                    |
| headless     | ✅ 容器无URL      | —                 | bot、worker、定时任务        |
| **小程序**   | ✅ 后端容器       | ✅ 客户端包       | 企微/微信小程序（前端+后端） |
| **桌面软件** | 可选(若带后端)    | ✅ 多平台安装包   | Electron/原生客户端          |
| 移动端       | 可选              | ✅ apk/ipa        | App/Flutter/RN               |
| CLI          | 可选              | ✅ 多平台二进制   | 命令行工具                   |

- **小程序 = 两态都有**：客户端走平台 CI 上传→审核→发布；后端走 app-space 部署。
- **桌面/移动 = 产物态为主**：交叉编译出多平台包，存 artifact store，靠下载页/自动更新/商店分发。

## 4. 分层目标架构

```
┌─────────────────────────────────────────────────────────────────┐
│ L6 体验层    应用为中心视图(拓扑/状态/日志) · 治理面(审批/配额/审计)        │
├─────────────────────────────────────────────────────────────────┤
│ L5 开发适配  编码工作台(opencode) · 导入分析 · 变更→审批→部署             │
├─────────────────────────────────────────────────────────────────┤
│ L4 治理脊柱(横切全应用、两态)                                             │
│   RBAC(部署权限分离) · 变更闸门 · 配额 · 版本/回滚 · 监控/日志/告警 ·      │
│   安全扫描 · 自动验收 · 审计                                            │
├─────────────────────────────────────────────────────────────────┤
│ L3 产物态    多平台构建(win/mac/linux·x64/arm64) · artifact store ·        │
│   分发渠道(下载页/自动更新源/微信CI上传/商店上架)                          │
├─────────────────────────────────────────────────────────────────┤
│ L2 供给绑定  dedicated(默认)/shared(可选)/bind-existing(导入) ·           │
│              连接注入(DATABASE_URL/REDIS_ADDR… env) · 凭证管理            │
├─────────────────────────────────────────────────────────────────┤
│ L1 运行态/app-space  每应用=一个 Docker 网络+一组类型化组件容器(声明式)     │
│   web·api·headless·data(pg/redis/milvus)·middleware                    │
├─────────────────────────────────────────────────────────────────┤
│ L0 运行时    Docker(不上K8s) · 多节点(docker -H) · 资源池 · 配额           │
└─────────────────────────────────────────────────────────────────┘
```

**运行态拓扑**：外部/app 间 HTTP → appgw → 各 app-space（网络隔离，内部服务名直连）→ 治理脊柱横切。

## 5. 各应用类型的开发与发布（端到端）

所有类型共用：**开发(opencode) → 变更登记 → 审批(闸门+RBAC) → 构建 → 发布 → 运维/审计**。差异在"构建+发布"语义：

| 类型          | 构建                                                   | 发布                                                                 | 健康/分发         |
| ------------- | ------------------------------------------------------ | -------------------------------------------------------------------- | ----------------- |
| web/service   | 镜像 build                                             | app-space 部署容器 + appgw URL                                       | HTTP 探活         |
| headless      | 镜像 build                                             | app-space 部署无URL                                                  | 进程存活/外连成功 |
| 小程序-客户端 | miniprogram-ci/wx devtools 编译上传包                  | 微信平台：上传体验版→审核→发布                                       | 微信侧版本/体验码 |
| 小程序-后端   | 镜像 build                                             | app-space 部署                                                       | HTTP/进程         |
| 桌面软件      | electron-builder/原生交叉编译(win/mac/linux·x64/arm64) | artifact store → 下载页/自动更新源(electron-updater latest.yml)/商店 | 已装客户端拉更新  |
| 移动端        | 构建 apk/ipa(多架构)                                   | artifact store → 商店上架/内测分发                                   | 商店版本          |
| CLI           | 多平台 go build/cargo 等                               | artifact store → 下载页                                              | 版本号            |

**关键**：产物态的多平台构建在**构建容器**里跑（`BuildConfig.build_image/build_command`，ANP 已有），产物存 artifact store（已有 `artifact_storage_local`），分发渠道是待补的主件。客户端发布同样过变更闸门 + RBAC（谁能发商店/微信）+ 审计 + 版本化。

## 6. 治理脊柱（横切，不分形态）

```
开发 → 构建 → 测试 → 变更闸门 → 发布 → 运维 → 审计/配额
opencode  各形态    test环境    RBAC+      运行态/   监控     变更记录
适配     构建      按形态健康  HasApproved 产物态    stop/start 安全扫描
                                                     日志 回滚  自动验收
```

- **全部已有**：RBAC（`app.deploy.test/prod`）、变更闸门（`HasApproved`）、配额、版本/回滚、监控、stop/start、日志、安全扫描（`artifact_scan`）、自动验收（qa）、变更审计。
- **按形态/态差异化的只有**：构建方式（镜像/产物）、发布目标（容器/商店/微信）、健康/分发判定。脊柱本身完全一致。

## 7. 依赖供给与互通

- **依赖供给三策略**：`dedicated`（每 app 自己实例，默认，PG 已是）/ `shared`（ANP 级共享+db号/前缀隔离，可选降本）/ `bind-existing`（绑定部署机已有服务，导入项目最常见）。应用声明依赖 → ANP 注入连接 env（扩 `DATABASE_URL` 范式到 `REDIS_ADDR`/`MILVUS_ADDR`/`PG_*`）。应用侧优先读 env（编码适配让 config 走 env 覆盖），无需 host 网络。
- **网络策略**：bridge 默认；`host` 网络按应用+审批+角色门禁（呼应"权限/风险"担忧），不默认开。服务只绑 loopback 时提示改 `0.0.0.0` / 绑可达实例 / 走 host（审批）。
- **应用间互通**：HTTP 走 appgw；内部服务互通走显式 peering（opt-in，默认 deny，留痕）。

## 10. 风险与取舍

| 风险                 | 应对                                                            |
| -------------------- | --------------------------------------------------------------- |
| host 网络削弱隔离    | 不默认开；按应用+审批+角色门禁；详情页标注；优先 bind 可达实例  |
| dedicated 资源成本   | 组件按声明供给 + shared 可选项 + 配额限容器数/内存              |
| 共享中间件多租户隔离 | db 号/namespace/前缀 + 配额 + 应用删除清理其数据                |
| 依赖注入密钥管理     | env 注入不落日志；复用 pgsupply 凭证范式，后续接 vault/KMS      |
| 客户端分发渠道碎片   | 抽象"分发渠道"接口（下载/自动更新/微信/商店），按 app_kind 选配 |
| 多平台构建矩阵成本   | 按需启用平台；构建缓存；交叉编译优先于多 OS runner              |
| 跨应用 peering 滥用  | 默认 deny + 显式审批 + 审计                                     |

## 11. 待审核的决议项

1. **app-space 组件粒度**：组件类型用 web/api/headless/data/middleware 这套，还是更粗/更细？
2. **依赖供给默认**：导入项目默认 `bind-existing` 还是 `dedicated`？（建议 bind + 提示）
3. **host 网络门禁**：复用变更闸门加网络策略字段，还是单设审批？
4. **产物态优先级**：先做"多平台构建+下载/自动更新"（桌面/CLI 通用），还是先做"小程序微信 CI"？（建议先通用下载/自动更新）
5. **小程序是否本期范围**：它两态都有、依赖微信侧能力，是否放远期？
6. **✅ 已定 — shared 中间件**：提供 ANP 级共享 redis/milvus 作为降本选项（**dedicated 默认 + shared 可选**，按应用声明选；shared 用 db 号/namespace/前缀隔离 + 配额 + 删除清理）。
