# pgsupply 生产健壮性 + 数据安全三项 实现记录（2026-07-22）

承接 `docs/superpowers/specs/2026-07-21-应用库与API统一管理-设计.md` §5（备份）/ I2（删项目级联）/ I5（并发），细化实现并部署 .28。

## 落地范围

| 项                      | 痛点                                     | 解法                                               |
| ----------------------- | ---------------------------------------- | -------------------------------------------------- |
| 1. 备份调度 + HTTP      | 应用库无自动备份（`Backuper` 写了没接）  | docker exec pg_dump + ticker(24h) + HTTP 触发/列举 |
| 2. 删项目级联清理（I2） | 删 project_space 只清 DB 行，PG 容器泄漏 | `TeardownForProject` + workspace 钩子              |

## 1. 备份（commit `626a7c3`）

**部署形态关键决策：backend 容器不含 postgresql-client**（`deploy/Dockerfile.backend` 仅装 `docker-cli`），故 `pg_dump`/`pg_restore` 走 `docker exec <pg容器>` —— PG 容器（pgvector/pgvector:pg16）自带 pg_dump，连 `localhost:5432 + PGPASSWORD`（从 `admin_url_ref` 解析）。

- `Backuper.BackupAll(ctx)`：遍历 `store.ListAppDBs("")` 逐个 Dump；失败记日志不中断；返回 `{total, success, failed, failed_app_ids}`。
- `Backuper.ListBackups()`：扫 `backupRoot/<psID>/<appID>/*.dump`，按 mtime 倒序。
- main.go 装配 `Backuper(Store, "/data/backups")` + `runBackupTicker`（默认 24h，`BACKUP_INTERVAL_HOURS` env 配，0=关闭，非法值回落默认）+ 优雅关闭（`ctx.Done` 停 ticker）。
- HTTP：
  - `POST /project-spaces/:id/apps/:aid/database/backup`（admin；`config.manage` 权限，guard.go 登记）：手动触发某应用库 Dump，返回产物路径。
  - `GET /pgsupply/backups`：列所有备份产物。
- 备份失败时产物文件 `os.Remove`（需先 `f.Close()` —— Windows 不能删正打开的文件，已修）。

## 2. 删项目级联清理（commit `595f430`）

- `InstanceManager.TeardownForProject(ctx, psID)`：列项目所有实例 → 有 `container_name` 走 `docker rm -f` + 删记录；无（external 或老实例）仅删记录；rm 失败保留记录便于排障。返回 `{total, removed, no_container, failed, failed_ids}`。
- `workspace.Service`：新增 `TeardownHook` 接口（`func(ctx, psID) error`） + `AddTeardownHook` + `DeleteProjectSpace`（先跑钩子→删 project_space 行，FK CASCADE 兜底数据行）。
- main.go 注入：`wsSvc.AddTeardownHook(instanceMgr.TeardownForProject)`。
- 路由：`DELETE /project-spaces/:id`（admin；`config.manage` 权限）。
- 钩子失败不阻塞删除（个别容器清理失败不卡删项目；数据级联由 FK CASCADE 兜底）。

## 3. 并发兜底（commit `6bd3e2b`）

- 迁移 000005 partial unique index `uq_pginstance_ps_active` ON `pg_instance(project_space_id) WHERE status='active'` —— 每项目至多 1 个 active 实例，DB 层兜底。
- `provision`：`CreateInstance` 失败时 `isUniqueViolation(23505)` 判定 → 清自己刚起的容器 → 重查 `GetInstanceByProject` 复用先到者建的实例；重查仍无则返回原错误。
- `isUniqueViolation` 用 `errors.As(*pgconn.PgError)` 解析错误码（pgx/v5/pgconn）。
- 走 `provision` 而非 `GetOrCreate` 是因为两并发都过 `GetInstanceByProject` 查无分支后才会同时到 CreateInstance 冲突。

## 4. 迁移 000005（与备份 commit 一起，因为 backup 也要 `container_name`）

`platform/backend/internal/db/migrations/pg/000005_pg_instance_container_and_unique.{up,down}.sql`：

- `ALTER TABLE pg_instance ADD COLUMN container_name TEXT`：provision 起的 PG 容器名，供备份 docker exec + 删项目级联清理。
- `CREATE UNIQUE INDEX uq_pginstance_ps_active ON pg_instance(project_space_id) WHERE status='active'`：并发兜底。

`provision` 写入 `ins.ContainerName = name`（容器名）。`instanceCols` 用 `COALESCE(container_name,'')` 处理历史行 NULL。

## 8. 顾虑与后续

- **备份保留策略未做**：当前每次 BackupAll 都新增产物，时间一长磁盘会涨。阶段 3 落「保留最近 N 份」+「按备份大小告警」。设计 §5.6 已规划。
- **备份产物恢复 HTTP 未做**：仅 `Backuper.Restore` 方法，无 HTTP 接口（恢复属敏感操作，admin 临时走 SSH 即可，待正式接口阶段 3 加 + 审计）。
- **未对 appdeploy_application 表的删项目级联做应用容器清理**：本任务的级联只清 PG 实例容器；appdeploy 自己的容器（test/prod 部署）的级联清理是另一条线（应由 appdeploy 注册自己的 teardown 钩子，类比 pgsupply）—— 后续 task。
- **`docker exec pg_dump` 在 PG 容器跑**：连接走 `localhost:5432`，跨主机不可用（仅适用于「backend 与项目 PG 容器同宿主」的当前部署形态）。多机化后需切换为远端 pg_dump 客户端或走 admin DSN。
- **跨主机 docker socket**：现 backend 容器装 `docker-cli` + 挂载 `/var/run/docker.sock`，pgsupply 通过 CLI 管容器。多机化或 K8s 化后此抽象要换（设计 §11 已提）。
