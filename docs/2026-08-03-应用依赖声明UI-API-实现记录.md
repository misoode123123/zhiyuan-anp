## 1. 做了什么

给 mwsupply（中间件依赖供给）补 **HTTP API + 前端「依赖」section**，替代开发者手编 `.anp/deps.yaml`。核心：**复用 `appdeploy_service_binding` 表做声明载体**（它本就具 `UNIQUE(app_id,service_kind)` + `status DEFAULT 'declared'` + 按 (app,kind) upsert——天然声明槽，declared 态此前闲置）。声明存平台 DB 为运行时真相，下次部署生效。

### 后端（7 任务）

- `mwsupply/store.go`：+`DeclareIfAbsent`（种子，`ON CONFLICT DO NOTHING`，不覆盖 UI 声明）+`DeclareBinding`（upsert declared，重置 instance/token）。
- `mwsupply/supply.go`：抽 `supplyAll(deps)`；`Reconcile` 读源从文件→DB binding（`ListBindingsByApp`→映射 DepService→supplyAll，去 repoDir）；+`SeedFromManifest`（导入种子）；+`ReleaseDep`（dedicated docker rm+删 instance+删 platform env+删 binding）；+`injectedEnvKeys`；+`ListDeps`/`SetDeps`(diff)/`DepsCatalog`。
- `mwsupply/store.go`：+`ListActiveInstances`（catalog 用）。
- `appdeploy/deps.go`（新建）：DTO（DepDeclaration/DepsCatalog/StrategyOption/CatalogInstance），定义在 appdeploy 避免 appdeploy↔mwsupply 循环。
- `appdeploy/handler.go`：MWReconciler 接口扩展（Reconcile 去 repoDir + SeedFromManifest/ListDeps/SetDeps/DepsCatalog）；+`GetDeps`/`PutDeps`/`GetDepsCatalog` handler（httpx 范式，3 参 `Get`，三类校验）；+3 路由；`runImport`/`runImportZip` 接 `SeedFromManifest`（UpdateImportDone 后/nil 守卫/ctx+repoDir）。

### 前端（1 任务）

- `app/applications/page.tsx`：自包含 `DepsSection` 组件（仿 ArtifactSection 范式，props psID/appID）挂每条 app 行（external app 不渲染）；列/增/删/改 kind+strategy（catalog 驱动下拉）→PUT 整体替换→toast「下次部署生效」。

### 关键决策

- **DB 为真相**（非仓库文件）：UI/API 独立编辑；`.anp/deps.yaml` 降为导入初始来源。
- **声明与部署解耦**：UI 改声明不触发部署；下次 deploy 时 Reconcile 读 DB binding 供给。
- **PUT 整体替换 + diff**：removed/changed→ReleaseDep，added/changed→DeclareBinding，unchanged→不动。
- **零迁移/新表/列/依赖**。

## 3. 教训 / 要点

1. **既有表常已预留所需**：`appdeploy_service_binding` 的 `declared` 态 + UNIQUE(app,kind) 是 P1 时为「声明+结果」设计的，P6 把闲置的 declared 态激活为声明载体 → 零迁移。**先读现有 schema 再决定是否新表**。
2. **接口演进须同步所有实现**：MWReconciler 接口加方法时，既有测试 fake（handler_http_test.go fakeMWReconciler）必须同步加 stub，否则测试包编译崩。计划里逐任务标注「同步 fake」步骤，避免了遗漏。
3. **brief 里的 `_ = func()` 是 Go 非法语法当 func 返 void**：supplyAll 返 void，brief 模板反复出现 `_ = r.supplyAll(...)`，implementer 每次修正为直接调用。写计划时对 void 方法别加 `_ =`。
4. **FK RESTRICT 删除顺序**：`binding.service_instance_id` 对 instance 是 FK NO ACTION（无 ON DELETE）→ 必须先删 binding 再删 instance，否则 instance 删不掉（错误被 best-effort `_ =` 吞→残留）。ReleaseDep 按 Cleanup 正确顺序（binding→instance）。
5. **写路径别吞错**：SetDeps 是用户写路径（PUT），瞬时 DB 错若吞→curMap 空→bound 被误 upsert 成 declared 丢 instance/token。final review 抓到→改为传播 ListBindingsByApp/DeclareBinding 错（ReleaseDep 保持 best-effort 即发即忘）。
6. **external app 不经 buildAndDeploy**：依赖声明对 external 无意义（Reconcile 不调→永不供给）。前端按 deploy_mode 门控不渲染 DepsSection。
7. **声明与部署解耦是正解**：PutDeps 只 diff+声明，不调 Reconcile；供给在下次 deploy。避免了「改声明即触发供给」的耦合。
